0.3.46: 修正启动预检的裸包名解析根 + 补退出原因台账

针对 2026-10-20 19:59 那次「弹窗 + 擅自禁用插件」的误伤。

一、判责结论（用户侧取证已给足证据）

  弹窗 + 擅自禁用   = DSH Desktop 自身缺陷（预检解析根取错树）   ≈85%
  配置引入         = session-70a33570 的 CLI Bridge 配置本身合法  ≈15%
  旧实例进程消失   = 不可指认（取证盲区，见第四节）

二、根因：解析根取错了树

预检（updater-backend.js preflightBareNameResolution）判断"裸包名能不能解析"
时，只从 <dsh-home>/profiles/<profile> 向上找 node_modules。而 DSH 运行时对
裸包名还有一层解析拦截（dsh-app-boot installRuntimeInterception，作用域是
installation scope = 官方后端安装树 <backend>/dsh/node_modules）。

这两个目录是兄弟、不是祖先 ⇒ 纯 walk-up 永远看不见官方包 ⇒ 官方包一律被判死。

  ❌ 旧口径只看这里            ✅ 运行时真实口径
  <dsh-home>/profiles/web/     <backend>/dsh/node_modules/  ← 被漏掉的那一棵
    └ node_modules               └ @deepseek-ai/dsh-mcp-client ✔

铁证：同名的 @deepseek-ai/dsh-mcp-resources 声明在**内置** dsh-base 补丁里一直
正常加载 —— 内置补丁就在 <backend>/dsh/node_modules/@deepseek-ai/dsh-base/，
恰好证明官方树里的裸包名是可解析的。

实测（backend\node.exe）：
  无拦截：dsh-mcp-client 与 dsh-mcp-resources 都 ERR_MODULE_NOT_FOUND
  有拦截：两者都 OK，installation scope 539 个包
  loader.internal 形状 = v2（判定看的是 cascaded loader 对象，不是模块命名空间
  —— 看命名空间会误判成"不可用"，我第一版探针就栽在这里）

四、本次落地的修复

  1. 新增 plugin-resolution.js：解析根模型重写
     - installation scope：Node 自己的 require.resolve.paths()（与 DSH 的
       installAnchor 同源）
     - local scope：profile 目录向上 walk-up
     - 口径保守放行：看得见就不禁（误禁代价远大于误放行）
  2. 自校验锚点：用内置 dsh-base 补丁里的裸包名当锚点；锚点解析不到 ⇒
     根集合不可信 ⇒ 拒绝任何破坏性禁用，只报告不删除（防同类复发）
  3. 自愈对称化：禁用时写机器可读标记（dsh-desktop:preflight-disabled …
     kind=…），启动时把"自己造成的、且现在能解析的"条目自动恢复；其它原因的
     禁用（loader id 冲突等）不动；历史条目用桌面日志取证（reason 含
     "冷启动必然失败"才算受害者）
  4. 新增 lifecycle-log.js：退出原因台账
     - 每次启动写 start、每条退出路径写带原因的 exit
     - 判读规则：有 start 无 exit ⇒ 进程没走到退出路径 ⇒ 外部强杀/断电
     - 覆盖托盘退出、窗口关闭、启动失败、更新重启、系统关机、渲染层崩溃、
       单实例、异常兜底
  5. 弹窗不再指死文件：日志路径改成绝对路径（本机同时有一个 9-10 起停更的
     同名死文件，那正是本次前期走偏的根源之一）
  6. 渲染层取证（对齐官方 main.ts:1110-1118）：补 render-process-gone /
     preload-error / unresponsive 监听 —— 渲染进程被 OOM 或被杀此前零证据
  7. 构建可复现性：install-backend.js 默认后端版本从 latest 钉成精确版本
     0.2.1-alpha.5（latest 是移动靶；子包 dist-tag 严重不一致，dsh-app-boot
     的 latest 还停在 0.1.0-rc.6）
