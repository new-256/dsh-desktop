> 产出任务：task-3。日期：2026-11-04。
> 配套文件：[能力对比矩阵.md](能力对比矩阵.md)（逐维度判定）、[结论摘要.md](结论摘要.md)（给用户看）。
> 官方证据路径前缀：`分析_官方桌面端对比_2026-11-04/01_官方侦察/upstream/apps/desktop/`（下称 `src/`）。
> 我方证据路径前缀：`C:\Users\<user>\Desktop\DSH\`。

## 判据（为什么是这些）

借鉴项必须同时满足三条，否则不进清单：

1. **对本形态成立**：我们是「独立外壳 + 自带运行时 + 面向普通用户」，不参与官方 monorepo 构建体系、没有官方服务端与账号体系。
2. **能指出用户可感知的收益**：不是"更优雅"，而是「不再挂死」「少一次 UAC」「反馈能定位」这类。
3. **能给出可量化的验收标准**：能被脚本或人工按步骤证伪。

三条之外还有一条硬纪律：**严禁为对标而硬编码**。所有方案必须是泛化设计（例如"通道由安装态决定"而不是"把 stable 写死成某个版本号"）。

**优先级定义**：P0＝立刻做，收益/成本比最高（多为 S 级纯逻辑改动）；P1＝一个迭代内；P2＝观察或暂不做。

# P0

## B-01 遗留 cookie 清理（端口无关）

**官方证据**
- `src/web-document.ts:58-70`：`removeLegacyHostCookies(cookies, url)` —— 注释原文点明机理：
  > "**Cookies ignore ports**, so cookies from earlier random-port Hosts would otherwise travel with every request to that hostname until they expire."
  实现：按 hostname 取 `dsh-auth-*` 前缀 cookie 并逐个 `remove`。
- 官方还在反代层剔除 `set-cookie` 响应头，让 cookie 归壳独占（`web-document.ts:78-82`）。

**我方现状（这是真 bug 类，不是"能不能更优雅"）**
- 后端以 `--port 0` 随机端口启动（`main.js:417`），但 **cookie 的作用域按 hostname 划分，端口不参与**（RFC 6265）。
- 全仓 `grep cookies|clearStorageData|session.fromPartition` **零命中** —— 我们对 cookie 完全没有任何处理。
- 后果：上一轮后端（旧端口）种在 `127.0.0.1` 上的 cookie，会被带到本轮**新端口**的请求里。若后端用 cookie 表达鉴权/会话上下文，就会出现"用旧 cookie 打新后端"的错乱。
- 与已发生故障的关联：CHANGELOG 0.3.25 记录过「重启后老页面指向旧端口 → 前端 `Failed to fetch`」。端口变化导致的陈旧凭证类问题，我们踩过一半（页面指向旧端口），另一半（cookie 跨端口串味）**从未被处理**。

**用户可感知收益**：消除一类"莫名要重登 / 接口莫名报错"的故障；重启后端后首次加载更干净。

**工作量**：S（一个函数 + 一处调用）

**风险与副作用**
- 清理范围必须**严格限定前缀**（例如只删本产品自己写入的 cookie 名），否则会误删同 hostname 下其它本地服务（其它 127.0.0.1 工具）的 cookie —— 这是唯一的真实风险。
- 必须在**已知后端 URL、loadURL 之前**执行，否则为时已晚。

**落点文件**
- `main.js`：后端 URL 确定后、`win.loadURL(url)`（`main.js:1426`）之前。
- 建议新建 `cookie-hygiene.js`（纯函数 + 依赖注入 `cookies`，便于测试）。

**可量化验收标准**
1. 连续启动两次（端口必然不同）后执行 `session.defaultSession.cookies.get({url:'http://127.0.0.1'})`，断言不含任何本产品前缀的 cookie 残留。
2. 同名但**不属于本产品前缀**的 cookie（先在测试里人为写入 `other-tool=1`）必须仍在 —— 证明没误删。
3. 新增脚本 `scripts/test-0XX-cookie-hygiene.js`：≥8 项断言，含"两轮端口不同仍清理干净""前缀不匹配不动""cookie store 抛错不阻断启动"。

## B-02 启动与停止的硬性 deadline（不允许永久 pending）

**官方证据**
- `src/host-process.ts:114-122`：`Promise.race([exit.then(() => true), timeout])` —— 所有等待都带 deadline，超时返回 `false` 而不是无限等。
- `src/host-process.ts:59`：`QUIT_INSPECTION_DEADLINE_MS = 2_000`，注释："a slower Host counts as unknown work and the shell asks before quitting" —— **超时不是失败，而是"按最坏情况处理"**。
- `src/fatal-recovery.ts:138-145`：崩溃报告落盘同样 `Promise.race` + `CRASH_REPORT_WAIT_MS`。
- `src/duration-env.ts`：统一的"可被 setTimeout 接受的时长"读取与校验。

**我方现状**
- `main.js:401-402` `spawnBackend()` 用 `new Promise(async (resolve, reject) => …)` —— **async executor 反模式**：executor 内异步抛出的异常只会 reject 那个被丢弃的 inner promise，外层 Promise 永久 pending。
- `waitForServer(url, 60000)` 只在"已从 stdout 抓到 URL"后才调用（`main.js:427-438`）；若后端既不打印也不退出，无人兜底。
- 整条 `whenReady` 链（`main.js:2265-2644`）**没有任何总预算或 `Promise.race`**。
- `main.js:121` 声明了 `QUIT_INSPECT_DEADLINE_MS = 2000` 并注释"对齐官方 2s"，**全项目零读取点**（化石常量）。
- 已在独立隐患清单中确认为 P0（H-02 / H-03）。

**用户可感知收益**：后端起不来时，用户在 90~120 秒内看到**一个明确的错误弹窗和可点的自救入口**，而不是盯着启动画面无限转、托盘永远显示"正在启动后端…"。

**工作量**：S

**风险与副作用**
- deadline 太短会把"慢但正常"的机器误判为失败（首次启动要解压/校验）。建议分档：首启 180s、常态 90s，并允许 env 覆盖。
- 必须走既有的 `stopBackendBounded()` + `showFatal()` 路径，不得新增一条平行的失败通道（否则自愈阶梯的登记纪律被绕开）。

**落点文件**
- `main.js:401`（把 async executor 拆成同步 executor + `boot().catch(reject)`）
- `main.js:427`（`waitForServer` 前后加总预算）
- `main.js:121`（让 `QUIT_INSPECT_DEADLINE_MS` 真正被使用，或在无用途时删除）

**可量化验收标准**
1. 注入一个"只 sleep 不打印 URL 也不退出"的假后端 → 断言在 `首启预算 + 5s` 内出现错误弹窗，且日志含明确的超时错误码（区分"未捕获到地址"与"地址已打印但无响应"两种）。
2. 注入一个"executor 内同步抛错"的路径（例如把 `nodeExe` 指向不存在文件）→ 断言 `spawnBackend()` **reject 而不是永久 pending**（用 5s 超时断言 + `Promise.race` 在测试里反向验证）。
3. 新增断言脚本 ≥10 项，其中至少 2 项是"故意制造挂起，断言不挂起"。

## B-03 更新轮询：单调时钟 + 完成起算 + 指数退避 + 抖动 + 单飞

**官方证据**
- `src/update-schedule.ts:93-104`：
  ```ts
  this.delay = failed ? Math.min(maxBackoffMs, this.delay * 2) : intervalMs
  const lower = Math.max(1_000, this.delay * (1 - jitter))
  const upper = Math.min(maxBackoffMs, this.delay * (1 + jitter))
  const delay = Math.round(lower + (upper - lower) * this.random())
  ```
- `src/update-schedule.ts:20-22`：默认 `intervalMs=600_000`、`maxBackoffMs=max(interval, 3_600_000)`、`jitter=0.2`，且**非法值直接抛错**（`:23-25`）而非静默回落。
- `src/update-schedule.ts:44-48`：`now` 默认 `performance.now()` —— **单调时钟，不受系统时间跳变影响**。
- `src/update-schedule.ts:59-77`：单飞合并（`pending` 复用）＋手动检查可 `force` 绕过 deadline，但**不绕过合并**。
- 注释（`:87`）点明"完成起算"：joined 的手动调用只推进一次重试延迟。

**我方现状**
- 后端更新：`setTimeout(checkBackendUpdates, 5000)` + `setInterval(checkBackendUpdates, 6*3600*1000)`（`main.js:1963-1964`）。
- 外壳自更新：`setTimeout(..., 10000)` + `setInterval(..., 24*3600*1000)`（`main.js:1705-1706`）。
- **无退避、无抖动、无单飞**：`setInterval` 不关心上一次是否还在跑；失败后仍按固定节拍重来；`Date.now()` 语义受系统时间调整影响。

**用户可感知收益**：弱网/机场/公司代理环境下，更新提示不再"要么一直不出现、要么一出现就卡"。失败后自动放慢，成功即回到常态节奏。

**工作量**：S（纯逻辑，无外部依赖 —— 侦察报告也把它列为三大高性价比项之一）

**风险与副作用**
- 退避上限必须有界（默认 1h），否则长期离线后用户永远等不到下一次检查。
- 抖动会引入非确定性，**测试须注入 `random`/`now`**（官方就是把两者做成构造参数，照此办理即可，无需 monkey-patch）。
- 不要改动"通知制"语义：本项只改**何时检查**，不改**是否自动下载**。

**落点文件**
- 新建 `update-schedule.js`（纯逻辑，可单测）
- 替换调用点：`main.js:1963-1964`、`main.js:1705-1706`

**可量化验收标准**
1. 注入 `now`/`random`/`check` 三个假实现，断言失败序列延迟为 `interval*2^n` 且不超过 `maxBackoff`（n=1..5）。
2. 断言抖动落在 `[delay*(1-j), delay*(1+j)]` 区间内，且 `j=0.2` 时重复 100 次采样不是常数。
3. 断言"上一次检查未完成时再次触发"只产生 1 次实际网络调用（单飞）。
4. 断言非法配置（jitter=1.5 / maxBackoff<interval）**抛错**而不是静默纠正。
5. 断言用 `performance.now()` 而非 `Date.now()`（把系统时间回拨 1 小时，断言不触发额外检查）。

## B-04 插件操作历史（环形日志）＋附进崩溃报告

**官方证据**
- `src/main.ts:530-532`：`segmentBytes: 256*1024, recordBytes: 4096, queuedBytes: 64*1024` —— 两段环形、单条 ≤4KiB、排队 ≤64KiB。
- `docs/diagnostics/README.zh.md:52`：目录 `userData/plugin-operations`，退出/恢复/安装准备最多等 **500ms** 排空；`:58` 持久化失败后**在本次壳生命周期内停用后续写入**（避免重复失败 I/O）。
- `src/operation-report.ts:36-38`：把最近操作**追加**到已写好的基础报告后，标题明确写
  > "recent plugin operations (**context, not proof of cause**)"
  并带"省略计数"与"收集完成"标记（`:38`、`:53`），不重写基础报告字节。
- `src/operation-report.ts:22-61`：整个附加段是 best-effort —— 失败时基础报告仍然可用。

**我方现状**
- `lifecycle-log.js` 记的是**启动/退出**（`start()`/`exit(reason)`/`note()`），`diag-log.js` 是**无结构流水**。
- **没有"当初谁装/禁/改动了哪个插件"的结构化记录**。
- 代价已经反复付过：CHANGELOG 0.3.24「清扫日志只写了数量，删的到底是谁，全靠文件时间戳反推」；0.3.26/0.3.37/0.3.41 三次事故的共性是「归因不到具体条目」。独立隐患清单的 H-11 也指出取证系统"只写不读"。

**用户可感知收益**：插件相关故障的诊断从「猜」变成「读」——用户反馈时我们能直接看到"故障前 30 秒装了什么、禁了什么、改了什么"。直接缩短"报障 → 修复"的往返次数。

**工作量**：M

**风险与副作用**
- **绝不能记凭据、token、完整路径以外的敏感内容**：只记"动作 + 插件标识 + 结果码"，不记命令行原文（`plugins:install` 的 spec 可能含私有 registry 地址）。官方在这一点上更严格——它连抛出的诊断串都特意避开插件 stderr，注释写明「arbitrary plugin stderr can contain credentials」（`src/host-process.ts:364`）。
- 环形写必须是**有界内存 + 有界磁盘**，否则从"取证"变成"新的启动税"（对照 H-09 的 `.bak` 堆积与 H-10 的同步写放大，不要重犯）。
- 只有"上下文"价值，**不得**让自愈阶梯把它当作因果证据（否则违反 `ladder-policy.js` 的 needs-proof 纪律）。

**落点文件**
- 新建 `plugin-ops-log.js`（环形段 + 单条截断 + 排队上限 + 失败停用）
- 写入点：`updater-backend.js` 的插件禁用/隔离/恢复路径（`disableFailingBundles`、`restorePreflightDisabledEntries`、`quarantineProfiles`）、`main.js` 的 `plugins:install` 通道
- 读取点：`crash-report.js` 的正文之后追加一段（对齐 `operation-report.ts` 的"context, not proof of cause"标题 + 省略计数 + 完成标记）

**可量化验收标准**
1. 写满 3 倍容量后，磁盘上仍只有 2 个段文件、总字节 ≤ 512KiB + 单段余量。
2. 单条超 4KiB 被截断且带 `truncated:true` 标记。
3. 退出/更新前排空等待 ≤500ms（注入慢磁盘，断言不超时）。
4. 注入写失败后，本次生命周期内不再尝试写入（调用计数断言）。
5. 崩溃报告同时包含：基础报告字节**未被重写**（前后 sha256 比对）、附加段含"context, not proof of cause"、含省略计数与完成标记。
6. 断言附加段不含凭据类键名（`token`/`password`/`secret`/`authorization` 白名单校验）。

## B-05 安全边界三件套：sandbox + 导航白名单 + 开窗默认拒

**官方证据**
- `src/main.ts:287-290`：主窗口 `nodeIntegration:false, contextIsolation:true, sandbox:true, webSecurity:true`；`browser-guests.ts:88`、`platform-view.ts:143`、`welcome-window.ts:44`、`update-overlay.ts:42`、`policy-test-auth.ts:76` 全部 `sandbox: true`。
- `src/web-document.ts:100`：`if (origin !== 'dsh-app://app') return new Response(null, { status: 403 })` —— 页面来源强制。
- `src/main.ts:852`：`!event.senderFrame.url.startsWith('dsh-app://app/')` 即抛错 —— IPC 与页面来源同源校验。

**我方现状**
- `sandbox: false`（`main.js:1328` 主窗、`main.js:1824` 设置窗）。
- `will-navigate` **零命中**（无导航白名单）。
- `setWindowOpenHandler` 只对 http(s) 做 `openExternal + deny`，**其余一律 allow**（`main.js:1165-1170`）。
- 设置窗根本没调用 `applyWindowHandlers()`（`main.js:1818-1829`）。
- 独立隐患清单 H-07 已单列为 P1。

**关键事实：这项成本极低。** 我方两个 preload 的依赖清单**只有 `electron`**（`preload.js` 全文 0.5KB，暴露 3 个 API；`settings-preload.js` 2.1KB，22 个通道），没有使用任何 Node 内置模块 → 开 `sandbox:true` **不损失任何功能**。

**用户可感知收益**：平时完全无感。收益在"出事时"——插件前端被投毒/页面被注入时，渲染进程拿不到原生能力，攻击面从"主进程级"降到"页面级"。对一个允许用户自由装第三方插件的产品，这是必须的兜底。

**工作量**：S

**风险与副作用**
- 需要回归验证 22 个设置通道 + 3 个主窗口 API（`sandbox:true` 下 `process.platform` 仍可用，但任何隐藏的 Node 依赖都会炸 —— 这正好是一次干净的体检）。
- 导航白名单要放行 `activeUrl`（后端随机端口，**每次启动不同**）与 `file://` 设置页；**不能**写死端口。
- `setWindowOpenHandler` 默认 `deny` 后，若某插件依赖 `window.open` 打开本地文件，需要显式加入白名单（按"应用自身拥有的 origin"判定，而不是按 URL 字符串）。

**落点文件**
- `main.js:1328`、`main.js:1824`、`main.js:986`（splash 也建议补 `sandbox:true`）
- `main.js:1165-1170`（开窗默认拒）
- `main.js:1818-1829`（设置窗补 `applyWindowHandlers`）

## B-17 下载包完整性校验（对 npm `dist.integrity` / `shasum`）

> 本项是在核对侦察报告 §6.6/§7.3 之后补列的：原清单只覆盖了"更新检查节奏"，漏了"下载下来的东西是不是我们要的那个"。

**官方证据**
- `src/update-journal.ts:12-13`：错误码白名单里含 `ERR_UPDATER_INVALID_SIGNATURE`、`ERR_UPDATER_CHECKSUM_MISMATCH` —— 说明官方把"签名不匹配""校验和不匹配"当作**一等公民错误**记录，而不是笼统的 download failed。
- `src/update-error.ts` + `src/update-coordinator.ts:257`：下载失败会被分类（`downloadFailureDetails`），不是一句 `error.message` 了事。

**我方现状**
- 运行时更新（`stageDsh`）从 npm/镜像下载后端 tgz，目前只做 **`content-length` 短读检查**（`updater-backend.js:615`、`:625`）。
- **未校验 `dist.integrity`（sha512）/ `dist.shasum`** —— 我们已经在 `updater-backend.js:663` 拉取了 registry 元数据（`object 里有 versions[v]`），哈希就在同一个文档里，**取用成本几乎为零**。
- 对照：**构建期**的 vendor payload 我们做得很好（8 个分卷 + 4 个关键文件 sha256，`scripts/write-vendor-manifest.js`），**运行期**的更新下载却是裸的 —— 这是一处明显的不对称。

**用户可感知收益**：镜像站同步不完整、CDN 截断、代理注入内容时，我们从"静默装上并运行一棵坏树"变成"当场判定损坏并重试/换源"。直接服务「总能打得开」。

**工作量**：S

**风险与副作用（必须诚实标注边界）**
- 本项防的是**传输损坏、截断、部分篡改**。它**不能**防"整个镜像站被恶意接管"——那种情况下元数据与 tarball 会一起被改，需要**签名信任根**（即 B-10 的资金问题）。**不要把它宣传成"供应链安全已解决"。**
- 部分老版本在 registry 元数据里可能缺 `integrity`（只有 `shasum`）→ 必须有明确的降级策略：优先 sha512，其次 sha1，都没有则**记日志并照常继续**（不能在无哈希可用时把用户卡死）。
- 校验失败要区分"可重试"（换源重下一份）与"两次都失败 ⇒ 判损坏并中止本次更新、保留现有版本"。

**落点文件**：`updater-backend.js`（下载/应用 `stageDsh` 路径，`:560-640` 与 `:663` 的元数据消费处）

**可量化验收标准**
1. 正常下载 → 校验通过，行为与当前一致（回归不破）。
2. 人为篡改 tarball 1 字节 / 截断 1 字节 → **拒绝安装**，报"校验失败"而非"下载失败"，且**不替换**现有后端。
3. 连续两次校验失败 → 中止并保留现版本，给出可操作提示（换源/稍后重试）。
4. 伪造"元数据缺 integrity 且缺 shasum" → 记一条明确日志后继续（不阻断）。
5. 断言校验失败的错误码进入更新 journal 的分类白名单（对齐官方 `ERR_UPDATER_CHECKSUM_MISMATCH` 的做法）。

**官方证据**
- `src/host-process.ts:363-366`：

- `src/update-coordinator.ts:213-218`：`install()` 先 `await this.beforeRestart()`，返回 false 就**退回 ready**（不装）。
- `src/main.ts:723-730`：Host 先 `lock` 拒新请求 → 等在途请求 → 再检查任务。
- `src/fatal-recovery.ts`：失败弹窗给的是**能真执行的动作**（禁用全部第三方插件 + 备份 patch → `.bak-<timestamp>` + 重启），不是摆设。

**我方现状（两个独立缺陷，都已在隐患清单确认）**
- **H-01**：`rollbackDsh()` 实现完整（`updater-backend.js:3825-3837`）、已导出（`:4551`），**全仓零调用点**；`showFatal()` 的 6 个按钮里没有"回滚到上一个版本"（`main.js:1598`）；`journalUnverified()` 只写日志（`main.js:2629-2634`），不改变任何行为。→ **回滚素材躺在磁盘上，用户拿不到**。
- **H-05**：`applyStaged()` 交换目录前后**没有"进行中"标记**（`updater-backend.js:3880-3917`），断电落在中间态时，下次启动 `ensureSeeded()` 会把后端**静默回退出厂版本**（`:1317-1322`）。

**工作量**：M

- 自动回滚必须设闸：**连续 2 次**启动失败才自动回滚，且必须留痕（否则会掩盖真根因，违反"不可逆操作需正面证据"的既有纪律 `ladder-policy.js:99`）。
- `apply-in-progress.json` 必须在**交换前**原子写入、在成功后删除；读到时优先恢复而不是 seed。

**落点文件**
- `updater-backend.js:3880-3917`（加 applying 标记）、`:3825`（`rollbackDsh` 接线路）、`:1317`（seed 前先读标记）
- `main.js:1598`（`showFatal` 加"回滚到上一个版本"，仅在 `dsh.previous` 存在时显示）、`main.js:2629`（`journalUnverified` 命中 → 作为回滚建议的依据）

**验收标准**
1. 伪造 `dsh.previous` 存在 + 后端启动失败 → 断言错误弹窗出现"回滚到上一个版本"，点击后 `dsh` 目录内容等于 `dsh.previous`，且 `versions.json` 被正确重写。
2. 连续 2 次启动失败 → 断言自动回滚发生，且日志与桌面报告各留一条明确记录；第 1 次失败**不得**自动回滚。
3. 更新应用前后端返回 `still-running` → 断言**不应用**更新且提示"下次启动生效"。
4. 交换中途注入失败（在 rename 之间抛错）→ 下次启动断言读取到 applying 标记、恢复到旧版本，**而不是**解压出厂版本。
5. 断言 `rollbackDsh` 至少有一个生产调用点（源码断言，防止再次变成死代码）。

## B-09 per-user 安装（消除 UAC 墙）——评估项

**官方证据**
- `scripts/electron-builder-config.mjs:267-270`：`nsis: { oneClick: false, perMachine: false, allowElevation: false, allowToChangeInstallationDirectory: false }`。
- 官方连"目录选择"都关掉，改用 `installer/path.nsh:127` 读注册表 `InstallLocation` 自管路径校验（报告 §7.1 已指出这处表里不一）。

**我方现状**
- `package.json:89-94`：`oneClick:false, perMachine:true, allowToChangeInstallationDirectory:true, allowElevation:true`；安装开始即请求提权（CHANGELOG 0.3.2）。

**为什么值得评估（这是"总能装得上"的直接变量）**
- `perMachine:true` = 必须管理员权限。在公司电脑、家长管控账号、UAC 被策略禁用的机器上，这一步**直接失败**。
- `perMachine:false` = 装到用户目录，**零 UAC**。
- 官方选择零 UAC，与它"桌面端只发 nightly、面向自家用户"的形态一致；我们面向的是"什么机器都要装上"的普通用户，这个变量的权重**比官方更高**。

**工作量**：M~L（要改安装路径、快捷方式、数据目录假设、卸载逻辑，且要保住"覆盖安装"与"结束进程"两条既有优势）

**风险与副作用**
- 一旦改为 per-user，`%PROGRAMFILES%` 下的旧安装无法直接被"覆盖升级"（跨作用域升级需要一段迁移或提示），这是**最大风险**。
- 我们已有 12 个历史安装包在 `release/`，存量用户的升级路径必须验证，不能只测全新安装。
- 不建议做成"两种模式都支持"——两条安装路径 = 两倍回归面，且用户分不清。

**建议做法**：先做**只读评估**（不改代码）：在一台"标准用户 + UAC 拒绝"的机器上实测当前安装器的失败点，并评估 per-user 迁移成本；结论再决定是否立项。

**落点文件**：`package.json` build.nsis 段、`build/installer.nsh`

**验收标准（评估阶段）**
1. 在"标准用户 + UAC 拒绝"环境下执行当前安装包，记录**确切的失败步骤与错误码**（这是决策输入，不是验收）。
2. 出一份 ≤2 页的结论：per-user 的迁移成本、存量用户升级路径、是否保留 perMachine。**不写完这份结论不动代码。**

3. `http://127.0.0.1:<当前后端端口>/x` → 放行；`http://127.0.0.1:<其它端口>/x` 按策略决定（建议放行 hostname 回环，因为端口每次启动都变）。
4. 纯函数单测覆盖上述 6 种输入，不吃 Electron 环境。

## B-12 最小 Electron 集成 spec + 期望文本快照

**官方证据**
- `apps/desktop/tests/` 约 **189 个 spec**，其中 `main-startup.spec.ts` 157KB、`update-coordinator.spec.ts` 20.8KB、`windows-installer-smoke.ps1` 16.5KB。
- `tests/expected/` 下大量**文本/JSON 快照**，且**成对存在 en / zh-CN 双语期望**（如 `fatal-dialog-en.txt` / `fatal-dialog-zh-CN.txt`、`update-restart-win32-en-US.json` / `-zh-CN.json`）。
- 覆盖取向：行为 + 输出文本双重锁定（例如 `welcome/{en,zh-CN}-{timeout,expired,waiting,api-key}.expected.txt`）。

**我方现状**
- 14 个 `scripts/test-0XX*.js`，自写断言计数（0.3.44 达 421 项），**质量取向是对的**（`test-045` 用假 session 驱动真实回调；`test-043` 强制在 Electron 里跑）。
- **但没有任何测试真正启动 Electron 主进程**（窗口/托盘/权限/关窗/quit-guard 全无自动化覆盖），也无 CI（H-16）。
- 代价已付：0.3.44「点复制即崩」在全绿情况下发布。

**用户可感知收益**：拦住"测试全绿但用户一点就崩"的回归。这是**我们唯一已经真实发生过的发布级事故类型**。

**工作量**：M

**风险与副作用**
- 不要追求官方那种 189 个 spec 的规模——那是专职团队的量。**只做 4 条**（见验收），每条都对应一次真实事故。
- 文本快照要**同时锁定中文文案**，否则改了文案没人发现；但快照更新必须有显式命令（不能自动 overwrite）。

**落点文件**：新增 `scripts/test-integration.js`（用 Electron 跑）+ `scripts/expected/*.txt`

**验收标准**
1. 一条 spec 启动主进程并断言窗口创建成功、`loadURL` 被调用。
2. 一条 spec 触发一次 clipboard 权限请求，断言**不崩**（直接对应 0.3.45 事故）。
3. 一条 spec 在未授权 sender 下调用 28 个通道之一，断言被拒（对应 0.3.42 的 `assertOwnedSender`）。
4. 一条 spec 断言错误框按钮文案与 `scripts/expected/fatal-dialog-zh-CN.txt` 一致（对应 0.3.46 那次"指向死文件"的文案变更）。
5. 4 条 spec 能在无显示器环境（CI/headless）下运行或明确跳过并说明原因。

# P2（观察 / 暂不做）

## B-13 诊断包一键导出（zip）
**官方证据**：`operation-report.ts`（附加段）+ `docs/diagnostics`；但官方形态是**单个 .log + 手动附加**，不是 zip 一键上传（报告 §8.3 明确）。
**我方现状**：只有"打开日志/打开日志目录/打开错误清单"（`main.js:1004-1006`、`:1903-1905`），用户反馈要自己凑 主日志 + 错误清单 + 错误报告 + lifecycle.log + crash-*.log + update-journal.json（H-14）。
**收益**：支持往返次数下降。**工作量** S。**风险**：必须白名单打包（绝不含 `dsh-home` 里的凭据文件），且要给出"包内清单"让用户自己看得见。
**落点**：`main.js` 托盘 + 设置窗。**验收**：一键产出 zip，内含 6 类文件且**不含** `.credentials.yaml` / `settings.json` 中的密钥字段（断言）；包内附 manifest 列出每个文件来源。
**为什么是 P2**：先把 B-04（结构化操作历史）做出来，诊断包才有值钱的内容；否则只是把现有日志打个包。

## B-14 窗口状态持久化
**官方证据**：`src/windows-layout.ts`（0.2KB，内容极薄）【未证实是否有 bounds 持久化】。
**我方现状**：窗口固定 `1440×920`（`main.js:1325`），全仓 0 处 `getBounds/setBounds`（H-14）。
**收益**：多显示器/小屏用户不用每次重摆。**工作量** S。**风险**：必须校验还原后的矩形仍落在当前可见显示器内（拔掉外接屏后不能把窗口放到不存在的坐标上）。
**验收**：最大化状态与位置可还原；断开显示器后启动回落到主屏可见区域。**为什么 P2**：纯体验，不影响"装得上/打得开"。

## B-15 安装器解压进度与阶段上报
**官方证据**：`installer/extract-progress.h`、`extract-report.h`(14.8KB)、`progress.h`、`pages.nsh` 366 行自绘四页；进度百分比锁定 7-Zip 解压器百分比，完成后 600ms 补满 100%。
**我方现状**：`build/installer.nsh` 只有一个版本选择页（`:11-28`），解压 228MB 期间进度是 NSIS 默认的粗粒度。
**收益**：装大包时不至于让人以为卡死。**工作量** M（要接 7-Zip 输出）。**风险**：NSIS 插件与 7za 输出解析易碎（我们的分卷是 8 个，进度要按分卷加权）。**为什么 P2**：0.3.2 已做过"并行解压提速 + 每阶段进度提示"，边际收益递减。

## B-16 文案字典化（i18n 前置准备）
**官方证据**：`src/locale.ts` 1559 行纯数据、8 语言；客户端 UI 硬编码文案被 `verify-client-ui-i18n` 拒绝；安装器 8 套 locale JSON。
**我方现状**：全中文硬编码散在 `main.js` / `settings.html`。
**收益**：将来做多语言的地基。**工作量** M。**风险**：这是**纯重构**，零用户可感知收益，且会大幅增加巨型文件的 diff 噪声（与 H-12 的拆分计划冲突，顺序要先拆后译）。**为什么 P2 / 暂不做**：我们的用户群当前全中文，投入产出比最低。侦察报告也把 8 语言安装器归为"品牌资产"。

# 顺带：不属于"借鉴"、但优先级高于以上全部的事

用户问的是"有什么可以借鉴"。但对比过程中确认的这 5 条**不是借鉴问题，是既有缺陷**，独立隐患清单已给出 P0 定级。**它们应当先于任何借鉴项处理**：

| 隐患 | 一句话 | 与本清单的关系 |
|---|---|---|
| H-01 | `rollbackDsh()` 是死代码，用户拿不到回滚 | → B-08 的一半 |
| H-02 | `spawnBackend` async executor 反模式 → 启动永久挂起 | → B-02 |
| H-03 | 全链路无启动超时 → 后端哑火即永久停在启动画面 | → B-02 |
| H-04 | profile 隔离兜底走 `rimraf` **直接删用户数据**，与 README 承诺相反 | 无对应借鉴项（官方无阶梯），**但这是最该先修的一条** |
| H-05 | `applyStaged` 无「进行中」标记 → 断电静默回退出厂版本 | → B-08 的一半 |

建议顺序：**H-04 → H-02/H-03 → H-05 → B-01 → B-05 → B-03 → B-04**。
其中 H-04 只需把兜底从"rename 失败就 rimraf"改成"copy 成功后才删、copy 也失败就放弃本轮隔离"，改动量与风险都极小，却能消掉一条**数据丢失**承诺违约。
