# 代码结构速览（DSH Desktop v0.3.47）

> 目的：让人在 5 分钟内知道「这个外壳由什么组成、依赖朝哪流、哪里是雷区」
> 取证基准：`C:\Users\lcl\Desktop\DSH` 现网文件（2026-11-04 读取）

## 1. 一张图看懂模块与依赖方向

```
                        ┌─────────────────────────┐
                        │  Electron 主进程入口     │
                        │  main.js  (2,703 行)     │  ← 既是窗口层、又是启动编排器、又是 IPC 层
                        └───────────┬─────────────┘
        ┌───────────────┬───────────┼────────────┬──────────────┬──────────────┐
        ▼               ▼           ▼            ▼              ▼              ▼
 updater-backend.js  diag-log.js  crash-report  lifecycle-log  quit-guard  ladder-policy
   (4,577 行)         (256)        (228)         (195)          (102)       (147)
   后端管理器/      日志+滚动     崩溃报告       退出原因台账    退出确认     阶梯纪律
   更新器/自愈引擎   +桌面报告                                  纯函数       纯函数
        │                ▲
        ├────────────────┘  (updater-backend 也写诊断日志)
        ├──────────────► plugin-resolution.js (245) ──► patch-file.js (146)
        │                裸包名解析根模型               补丁文件解析原语（纯函数）
        └──────────────► patch-file.js

 渲染层侧（独立进程，只能通过 preload 白名单进主进程）：
   main window ── preload.js (13 行，2 个通道)
   settings window ── settings-preload.js (36 行，约 30 个通道)
   splash window ── 无 preload，无 IPC

 构建期（不随运行期加载）：
   scripts/install-backend.js (11.9KB) → vendor/dsh
   scripts/prepare-runtime.js (15.2KB) → vendor/runtime
   scripts/pack-vendor.js (12.2KB) → build/payload/vendor-*.7z
   scripts/write-vendor-manifest.js (8.8KB) → build/payload/vendor-manifest.json
   build/installer.nsh (172 行) → NSIS 钩子
```

**依赖方向结论**：严格单向、无环。三个纯函数模块（`quit-guard` / `ladder-policy` / `patch-file`）不依赖 Electron、可单测——这是本项目架构上最正确的一步。`plugin-resolution` 只依赖 `patch-file` + Node 内建。

**分层结论**：`main.js` **没有分层**——它同时承担 ①窗口/托盘/生命周期 ②启动编排（17 个步骤）③28 个 IPC handler ④设置窗控制器 ⑤权限闸门 ⑥自愈阶梯调度。这是全项目最大的结构性问题。

## 4. 数据与状态所在（谁拥有什么）

```
%APPDATA%\DSH Desktop\                     ← app.getPath('userData')
├─ backend\                                ← 活跃运行时（可重建，non-precious）
│  ├─ node.exe / node_modules\{npm,corepack}
│  ├─ dsh\node_modules\@deepseek-ai\dsh     ← 活跃后端
│  ├─ dsh.new\      ← 暂存（下次启动应用）
│  ├─ dsh.previous\ ← 上一个版本（**回滚素材，但无人使用**）
│  ├─ node.new\     ← 暂存 Node
│  ├─ downloads\    ← node zip
│  ├─ versions.json / update-journal.json / plugin-isolation.json
│  ├─ safe-mode.json / python-check.json / combo-gate.json
│  └─ settings.json ← 更新路线（npmRegistry/nodeDist）
├─ dsh-home\                               ← **用户数据（precious）**
│  ├─ cordis.patch.yml                     ← 家级插件补丁（会被自动手术）
│  ├─ .credentials.yaml                    ← 凭据（会被键名规范化）
│  ├─ profiles\{web,...}\                  ← 插件注册（可被隔离重建）
│  ├─ node_modules\                        ← 自定义插件 junction（家级，隔离后幸存）
│  ├─ plugins-store\, sessions\, storages\
│  └─ *.bak × 6 类                         ← 备份（无清理）
├─ bin\                                    ← 终端包装器 dsh.cmd / dsh-desktop.cmd
└─ logs\                                   ← 不可写安装目录时的回退位置

<安装目录>\logs\                            ← 打包态首选日志目录
<桌面>\DSH-Desktop-错误报告.txt             ← 固定名，仅当前这一份
```

**关键所有权判断**（决定改动的风险等级）：
- `backend/` 之下**全部可重建** → 改动风险低，最坏是重新 seed。
- `dsh-home/` 之下**全部是用户数据** → 任何写操作都必须先备份，任何删除都必须先隔离。`quarantineProfiles` 的 `rimraf` 回退（`updater-backend.js:1711-1719`）违反了这个原则。

## 5. 两条关键时序（读懂它们等于读懂这个外壳）

### 5.1 启动时序（正常路径）

```
app.whenReady
 → diagLog.housekeep()                       ← 保留期清理
 → createSplash()（非 --hidden）
 → createTray()                              ← **先建自救入口**，此刻 bootPhase='starting'
 → ensureSeeded()                            ← 首次/缺失部件时解压 payload（同步，可能数十秒）
 → writeWrapperScripts() + preseedDshHomeEnv()
 → requestedBackendVersion() → 按安装选择暂存一次 → 清除标记
 → applyStaged()                             ← 更新在此生效（后端未运行 → 无文件锁）
 → applySafeModeBoot(argv)                   ← 安全模式标记解析 / 崩溃后自动还原
 → recoverInterruptedIsolation()              ← 上次死于逐插件轮测则补完
 → nodeRequirement() → 不满足则 ensureNodeMeetsRequirement()
 → repairProfileJunctions()                   ← 修 junction（每次启动都做）
 → migrateAgentPresetPersonaText()            ← text→prefix 迁移
 → validateAndRepairPatchLayers()             ← 补丁结构预检
 → findLoaderIdConflicts() + restorePreflightDisabledEntries() + preflightBareNameResolution()
 → comboGateCheck() / pythonBootCheck() / validateCredentialsDocument()
 → startBackendWithPluginIsolation(shouldIsolate)
      └─ spawnBackend()  ─ 失败则进 8 级阶梯（见 5.3）
 → createMainWindow(url) → createTray()（升级为 running 菜单）
 → journalMarkVerified() + setupShellUpdater() + scheduleSilentUpdates()
```
失败汇聚点：整条链任一环节 throw → `showFatal(err)`（`main.js:2642-2644`）→ 托盘保留自救入口 + for(;;) 恢复弹窗。

### 5.2 更新时序（通知制）

```
[每 6h] checkBackendUpdates()
   → mgr.checkForUpdates()  (GitHub ∩ npm 双源)
   → 有更新：仅 setUpdateStatus('available') + 托盘气泡 + 日志   ← **不下载**
   → 已有暂存：'ready'

[用户点「设置…」→「检查更新」→「下载并更新」]
settings:download-updates
   → 再 check 一次 → 弹确认框（版本差异 + 上游改动）
   → stageConfirmedUpdates()  → mgr.stageDsh() 装进 dsh.new / stageNode() 解压进 node.new
   → 弹「立即重启并更新 / 稍后」
   → restartApp() → app.relaunch()

[下次启动]  applyStaged() 把 dsh.new → dsh（旧版进 dsh.previous）
```

**断点**：`dsh.previous` 保留着、`rollbackDsh()` 写着、journal 记着 `applied`——但**没有代码在启动失败时调用它们**。整条链的"失败支路"是断的（详见《隐患清单》H-01）。

### 5.3 自愈阶梯（唯一需要"读注释才能安全修改"的地方）

```
spawnBackend 失败
 → R0  原样重试 1 次（吸收更新后文件未落定的竞态）
 → 0a  补丁结构损坏？     → 补 [] / 回退备份          [可逆]
 → 0   补丁条目冲突？     → 只禁冲突条目              [需点名]
 → 1a  junction 损坏？    → 重建 junction             [可逆]
 → 1b  日志点名补丁条目？ → 只禁该条目                [需点名]
 → 1c  日志点名 bundle？  → 只移出加载清单            [需点名]
 → 1d  凭据键非法？       → 规范键 + **登记 guardReason**（否决后续不可逆级）
 → 2   profiles 可疑？    → 隔离整棵 profiles（要求**正面证据**）  [不可逆]
        └─ 成功后自动还原第三方注册；还原后起不来则回滚还原
 → 3   node.exe 缺失？    → 重装 Node                 [不可逆]
 → 全失败 → throw firstErr → showFatal
```
每一级的允许/拒绝由 `ladder-policy.attemptStage()` 裁决，裁决写进 `ladderTrail` 并落日志（`main.js:458-462`）。

## 7. 修改风险地图（给后续开发者）

| 区域 | 风险 | 原因 |
|---|---|---|
| `ladder-policy.js` 的 STAGES 表 | **高** | 新增/删除自愈级会改变阶梯下坠路径；必须同步 `main.js` 的调用点与证据判定 |
| `updater-backend.js` 的 patch 手术函数族（`commentPatch*` / `disablePatchEntriesInFile` / `restorePreflightDisabledEntries`） | **极高** | 直接改写用户配置文件；解析模型一旦分叉就会出现"预检认为能装、归因认为装不上"的自相矛盾（`patch-file.js:4-13` 记录的 2026-10-20 事故） |
| `analyzeEnvIsolation()` | **高** | 顺序敏感；写错会导致后端拿到污染环境 → 表现为无法归因的启动失败 |
| `applyStaged()` | **高** | 文件交换是唯一不可逆窗口；改错 = 后端丢失 |
| `applyPermissionGates()` | **高** | 回调里的异常会直接崩主进程（0.3.45 已发生一次） |
| 各 `diag-log` / `crash-report` 的 catch | 低 | 明确纪律"诊断绝不抛错"，改错只影响日志 |
| `quit-guard` / `ladder-policy` / `patch-file` 单测 | 低 | 纯函数，`scripts/test-04x.js` 有覆盖 |

## 8. 测试与验证现状（顺带盘点）

- `scripts/` 下有 14 个自测脚本（`test-038` … `test-047-desktop-report`、`test-manifest-verify`、`test-packaging`、`test-043-ladder`、`test-045b-copy-e2e`、`verify-041-real`、`verify-043-incident`、`verify-043-real`），CHANGELOG 逐版本记录断言数（如 046 → 34 项、047 → 15 项）。
- 全部是**独立 node 脚本**，无统一 runner、无 CI 配置（仓库无 `.github/`）。
- 覆盖偏向"纯函数 + 单点修复回归"，**没有任何 Electron 主进程集成测试**（窗口/托盘/权限/IPC 全无自动化覆盖）——这正是 0.3.44「点复制就崩」能在发布版里活下来的原因。
