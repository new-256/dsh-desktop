## H-01 [P0] 更新装坏了没有自动回滚 —— 回滚能力是「写着但没接电」

**证据**
- `rollbackDsh()` 完整实现：`updater-backend.js:3825-3837`（把坏 `dsh` 改名为 `dsh.failed`、把 `dsh.previous` 换回 `dsh`、重写 `versions.json`）。
- 已导出：`updater-backend.js:4551`。
- **全仓零调用点**：`grep -n "rollbackDsh" *.js` 只命中定义与导出（另有 `scripts/test-*` 未覆盖它）。
- 旧版本确实被保留：`applyStaged()` 在交换成功后执行 `rimraf(dsh.previous)` + `rename(dsh.old → dsh.previous)`（`updater-backend.js:3894-3895`）—— 素材齐全。
- 启动失败时的现状：`showFatal()` 弹 6 个按钮（查看日志/修复插件配置/安全模式/重试/留托盘/退出，`main.js:1598`），**没有「回滚到上一个版本」**。
- journal 侧：`journalUnverified()` 被调用后只写一行 diag + pushLog（`main.js:2629-2634`），不改变任何行为。

**触发条件**：任何一次 `stageDsh` 成功、`applyStaged` 成功、但新后端起不来的更新（上游破坏性变更、依赖缺失、Node ABI 变化）。这是**必然会发生**的一类事件，不是极端假设。

**后果**：用户的应用从"能用的旧版"变成"打不开"，唯一的自救路径是 ①托盘→设置…（仅在 `bootPhase==='failed'` 时启用，`main.js:1056`）②在全部 npm 版本里自己挑一个 ③理解"回退"要靠暂存新版本而不是换回 `dsh.previous`。回滚素材就躺在磁盘上，用户拿不到。

**建议**（三步，按性价比排序）
1. `showFatal` 的按钮列表加「回滚到上一个版本」（当 `dsh.previous` 存在时）→ 直接调 `rollbackDsh()` + `restartApp()`。
2. 启动失败**连续 2 次**时自动执行 `rollbackDsh()`（并在日志/弹窗说明"已自动回滚到 vX"），把 `journalUnverified()` 从"记录"升级为"决策依据"。
3. `journalUnverified()` 命中时在启动后弹一次一次性提示，而不是只写日志。

## H-02 [P0] `spawnBackend` 的 async executor 反模式 → 启动永久挂起

**证据**：`main.js:401-402`
```js
function spawnBackend() {
  return new Promise(async (resolve, reject) => {   // ← executor 是 async
```
executor 体内可能同步抛出的调用（**未被任何 try/catch 包住**）：
- `mgr.buildDedicatedEnv()`（`main.js:410`）→ 内部 `mkdirp()` 是裸 `fs.mkdirSync`（`updater-backend.js:503`、`151`）：`%APPDATA%` 权限异常 / 磁盘满 / 杀软拦截 → 抛
- `spawn(p.nodeExe, args, …)`（`main.js:419`）→ `EACCES`/`EPERM` 同步抛出

**机制**：async 函数体内抛出的异常只会 reject **该 async 函数自己返回的 Promise**，而这个 Promise 被丢弃。外层的 `new Promise(...)` 既不 resolve 也不 reject → **永久 pending**。

**后果**：`await startBackendWithPluginIsolation(...)`（`main.js:2612`）永不返回 → `whenReady` 的整条链停在第 5 步 → 外层 `catch (err) { showFatal(err) }`（`main.js:2642-2644`）**永远不执行**。用户看到：启动画面一直转、托盘菜单一直是「正在启动后端…」。既没有错误弹窗，也没有日志里的失败记录（只有 `pushLog` 之前的内容）。

**建议**：把 executor 改成同步函数（内部用 `async function boot()` 再 `.catch(reject)`），或至少整体 `try { … } catch (e) { reject(e) }`。同时给 `mkdirp` 类调用加可读错误信息。

## H-03 [P0] 全链路没有启动超时

**证据**
- `waitForServer(url, 60000, cb)` 只在"从 stdout 抓到 URL 后"才会被调用（`main.js:427-438`）。
- 若后端既不打印 URL 也不退出（例如启动卡在插件安装/网络请求/文件锁），`spawnBackend` 的 Promise 不会 settle。
- 全仓无「启动总预算」：`whenReady` 链（`main.js:2265-2644`）从头到尾没有 deadline，也没有 `Promise.race` 超时。

**触发条件**：后端启动阶段挂住（插件安装锁、镜像请求无响应、`dsh web` 初始化卡死）；或上游把 `dsh web: <url>` 的日志格式改掉（正则 `main.js:428` 失配）。

**后果**：与 H-02 同表现 —— 启动画面永久停留，只有托盘的「重试启动」能人工干预，且重试会再走一遍同样的路径。

**建议**：给 `spawnBackend` 加 90~120s 全局 deadline（`Promise.race` + `reject(new Error('后端启动超时…'))`），超时走既有的 `stopBackendAndWait()` + `showFatal` 路径；并把「未捕获到后端地址」与「地址已打印但无响应」区分成两个错误码。

## H-04 [P0] profile 隔离的兜底分支是直接删除用户数据

**证据**：`updater-backend.js:1707-1720`
```js
try { fs.renameSync(prof, targetPath); quarantined = true; }
catch (e) {
  log(`rename profiles to ${targetName} failed (${e.message}); falling back to rimraf`);
  try { rimraf(prof);            // ← 整棵 profiles 目录被删除，不是隔离
        quarantined = true; fallback = true; } catch …
}
```
- 唯一的补偿是此前写入的 `profiles-registry-<ts>.json` 快照（`updater-backend.js:1691-1702`），它只保存 bundles / dependencies / patch 文本，**不保存 profile 内的 node_modules 实体、不保存其它 profile 文件**。
- `pruneQuarantineProfiles()` 只保留最近 2 份隔离目录（`1597-1624`），配合本分支等于"删了就没有"。
- 与承诺冲突：`README.md:63` 明写「启动自愈最坏的情况也只是把 profiles 隔离备份成 `profiles.broken-时间戳`（保留最近 2 份），**不删任何数据**」。

**触发条件**：rename 失败 —— Windows 上典型原因是旧后端进程未完全释放句柄、杀软/索引服务正在扫描 `profiles`、或者目标名冲突后仍失败。

**后果**：用户的插件注册树被物理删除；自动还原（`restoreProfileRegistrations`，`main.js:846`）只能恢复 package.json 里的名字，**依赖实体已丢**，表现为"插件都还在但都装不上"。

**建议**：兜底改为「copy 到 `profiles.broken-<ts>` 成功后再删原目录」，copy 也失败就**放弃本轮隔离**（阶梯本来就允许跳过，`ladder-policy.js:99-110`）；并在 README/弹窗里修正这句诺言。

## H-05 [P0] `applyStaged` 没有「进行中」标记 → 断电后静默回退出厂版本

**证据**：`updater-backend.js:3880-3917`
```
for (attempt 1..4) {
  rimraf(dsh.old); rename(dsh → dsh.old); rename(dsh.new → dsh); …
}
```
- 交换过程中存在两个窗口：`dsh` 不存在（中间态）、`dsh.new` 已消费。
- 只有在交换**成功之后**才写 journal（`journalAdd('dsh','applied')`，`3916`），**没有写入 "applying" 状态**。
- 若在这两个窗口内进程死亡（断电、强杀、BSOD），下次启动：`ensureSeeded()` 判定 `needDsh = !fs.existsSync(p.dshBin)`（`updater-backend.js:1317-1322`）→ 直接从 payload 解压**出厂版本 0.2.1-alpha.5**。

**后果**：用户的后端被静默降级到出厂版本，`dsh.previous`（本该是回滚目标）变成了"比现在更新"的版本，`versions.json` 被覆盖。表现为「昨天刚更新，今天又变回去了」，且日志里只有一行 seeding 记录。`dsh.old` 目录还会残留。

**建议**：交换前写 `apply-in-progress.json{from,to,at}`，启动时先读它：存在则优先用 `dsh.old`/`dsh.previous` 恢复并在 UI 上报告"上次更新被中断，已恢复/回滚"，而不是让 seed 逻辑接管。另外 journal 加 `applying` 态。

## H-06 [P1] 设置窗 `innerHTML` 拼接外部字符串 → 高权限窗口里的脚本注入面

**证据**
- 拼接点：`settings.html:439-447`（`legacyScan.home`、`o.name`、`o.version`）、`319-325`（`row.name`、`row.reason`、`row.nodeEngine`）、`467-470`（`x.name`、`x.reason`）、`437-438`。
- CSP 允许内联脚本：`settings.html:5` `script-src 'self' 'unsafe-inline'`。
- 注入源的来源链：插件名 = profile `package.json` 的 `dsh.profile.bundles` / `dependencies` 键（`updater-backend.js:4139-4158` 原样返回 `String(name)`，无转义）；`reason` 来自 manifest 字段与日志文本（`updater-backend.js:3746-3800`）。
- 该窗口的桥权限：`settings-preload.js:25`（`plugins:install` → `dsh plugin add <spec>` → pnpm 安装 → **postinstall 脚本执行**，见 `updater-backend.js:4418-4445`）、`settings-preload.js:17`（`backend:rollback-to`）、`settings-preload.js:23`（`plugins:set-path-entry` → 改用户 PATH）。

**触发条件**：`dsh-home` 或 `~/.dsh` 的 profile 注册里存在一个名字含 HTML 的条目（插件作者可直接控制 `name` 字段；本地目录名亦可被构造），用户在设置窗点「扫描旧 Home」或「分析兼容性」。

**后果**：注入的 `<img onerror=…>`/内联脚本在该窗口执行 → 可调用上述高权限 IPC → 安装任意 npm 包并执行其 postinstall = **代码执行**。前提是攻击者已能让一个恶意包名出现在用户 profile 里（供应链/手动安装），属"二段跳"，但这段跳跃完全没必要存在。

**建议**：`settings.html` 全部改 `textContent` / `document.createElement` 构表（或引入一个 `esc()` 并强制走它）；把 CSP 的 `'unsafe-inline'` 去掉（把内联 script 抽成 `settings.js` 文件）。另建议 `plugins:install` 在设置窗侧加一次显式确认（当前是即时执行）。

## H-07 [P1] 渲染层隔离与导航边界粗糙

**证据**
- `sandbox: false`：主窗 `main.js:1328`、设置窗 `main.js:1824`。
- `will-navigate` 全仓 0 命中（无任何导航白名单）。
- `setWindowOpenHandler` 只对外部 http(s) 做 `openExternal` + deny，**其余一律 `allow`**：`main.js:1165-1170`。
- 设置窗根本没有调用 `applyWindowHandlers()`（`createSettingsWindow`，`main.js:1818-1829`）。

**触发条件 / 后果**
- `sandbox:false` + 渲染层被 XSS：攻击者从页面上下文直接拿到有完整 Node 能力的 preload 环境，`contextBridge` 白名单形同虚设。
- 无 `will-navigate`：后端页面里一个普通链接即可把整个窗口导航到外部站点（用户失去 UI；server 侧 token 泄漏风险由后端承担，不由外壳兜底）。
- 非 http(s) 放行开窗：`window.open('file:///C:/…')` 等会真的开出一个新 BrowserWindow（无 preload，但共享 session）。

**建议**：`sandbox: true`（当前 preload 只用 `ipcRenderer`，完全兼容）；加 `will-navigate` 白名单（只允许 `activeUrl` 与 `file://<apppath>`）；`setWindowOpenHandler` 默认 `deny`，只 `allow` 同源 `about:blank`；设置窗也调用 `applyWindowHandlers`。

## H-08 [P1] 缺 AUMID，唯一的主动通知通道可能完全失效

**证据**
- `tray.displayBalloon()` 是**唯一的主动提醒通道**：更新可用（`main.js:1692`、`1737`）、启动失败（`main.js:1564`）。
- 全仓 **0 处 `app.setAppUserModelId()`**（grep 命中只有 `setLoginItemSettings`）。
- 对照：`package.json:32` 有 `appId: com.deepseek.dshdesktop`（安装器快捷方式会用），但进程侧没有把 AUMID 与之一致化。

**触发条件**：Windows 10/11 上，未设置 AUMID 的进程调用托盘气泡，系统会静默丢弃（不出错、不报错）。

**后果**：用户永远收不到"有新版本"的提示，也收不到"启动失败"的提示 —— 更新链路的第一环断了，只能靠自己想到去开设置窗点检查；启动失败时托盘图标本身仍是自救入口，但用户不知道要去看它。

**建议**：`app.setAppUserModelId('com.deepseek.dshdesktop')` 放在 `whenReady` 之前；并在首次气泡后用 `log` 记录一次「气泡已发出」以便事后判断是否被系统吞掉【待确认：本机实际能否显示，需实机验证一次】。

## H-09 [P1] 六类 `.bak` 备份无清理策略

**证据**
| 备份类 | 写入点 | 清理 |

| `<patch>.disabled-<ts>.bak` | `updater-backend.js:2673` | **无** |
| `<patch>.broken-<ts>.bak` | `updater-backend.js:2121` | **无** |
| `<patch>.restore-<ts>.bak` | `updater-backend.js:2902` | **无** |
| `cordis.patch.yml.isolation-<ts>.bak` | `updater-backend.js:2018` | **无** |

**二次伤害**：`restorePreflightDisabledEntries()` 每次启动要把每个补丁文件的**全部** `.disabled-*.bak` 读进内存并逐个比对（`updater-backend.js:2755-2791`，且外层是 `while (progress)` 反复扫描）。备份越多，启动越慢 —— 而"启动失败"恰好是产生备份的场景，形成正反馈。

**建议**：给这 6 类备份加统一保留策略（每类保留最近 3~5 份 + 30 天，复用 `diag-log.js:125-144` 的 `pruneArchives` 模式，注意沿用"只删能解析出时间戳的我方文件"的 P2-2 纪律）。

## H-10 [P1] 每条后端输出都付一次同步文件系统调用

**证据**
- 后端 stdout 每来一行 → `pushLog()` → `diag('后端输出', text)`（`main.js:210-221`，`219-220`）。
- `diag-log.write()` 每次调用：`rotateIfNeeded()` → `fs.statSync`（`diag-log.js:113`）→ `fs.appendFileSync`（`243`）→ `ERROR_LINE_RE.test` → 命中错误时再 `statSync` + `appendFileSync` ×2（`221-223`）。
- 全部在 Electron 主进程、**同步**。

**触发条件**：后端高频输出（插件批量构建、长任务进度、错误风暴）。

**后果**：主进程事件循环被同步 I/O 占用 → 窗口响应变慢/卡顿；同时把后端日志全文复制一份进诊断日志（磁盘写放大 2×，日志 10MB 滚动得更快）。

**建议**：改为「内存环形缓冲 + 200ms 批量 flush」（用 `fs.promises` 或 `writeStream`）；滚动阈值检查降到每分钟一次；后端原始输出单独降级为 `debug` 级（默认不落盘）。

## H-11 [P1] 取证系统「只写不读」—— 辛苦记录的结论没人消费

**证据**
- `lifecycle.readOrphanSessions()`（判断"上次是被外部强杀"）在 `lifecycle-log.js:168-181` 实现，**主进程零调用**（仅 `scripts/test-046-preflight-resolution.js:210` 使用）。
- `journalUnverified()` 的消费端只写日志不动作：`main.js:2629-2634`。
- `QUIT_INSPECT_DEADLINE_MS`（`main.js:121`）注释自认"从未被任何代码读取"。
- `quitGuard.suppress()`（`quit-guard.js:95`）无调用 —— 「记住我的选择」不存在，用户每次退出都被问。

**后果**：这些能力的实际价值退化为"文件里有记录，但用户和 UI 都不知道"。特别是"上次被强杀"这个结论——它本该在启动时变成一句"检测到上次异常退出，已为你保留会话/建议查看日志"。

**建议**：`whenReady` 开头调 `readOrphanSessions()`，命中则写日志 + 一次轻量提示（不要弹窗，用托盘 tooltip/设置窗状态）；`journalUnverified()` 命中接 H-01 的回滚建议；`suppress()` 接上「不再询问」按钮（退出确认框加第三按钮）。

## H-12 [P2] 巨型单体 + 超长函数 + 156 处空 catch

**证据**
- `main.js` 2,703 行 / `updater-backend.js` 4,577 行，两者合计 7,280 行（占运行期 JS ≈93%）。
- `startBackendWithHealing()` 单函数 **444 行**（`main.js:465-908`），含 11 个 try/catch、8 级阶梯、5 个跨分支可变状态。
- 空 catch 统计（`catch { }` / `catch (_) { }` 形式）：`main.js` 77 处、`updater-backend.js` 54 处、`diag-log.js` 12、`lifecycle-log.js` 6、`crash-report.js` 5、`plugin-resolution.js` 1、`patch-file.js` 1，**合计 156 处**（`quit-guard.js` / `ladder-policy.js` 为 0，纯函数模块纪律良好）。

**说明**：空 catch 中很大一部分是**正确的纪律**（"诊断日志绝不抛错"、"台账绝不抛错"）。但其中也有真实故障被吞掉的地方，例如 `updater-backend.js:1714-1719`（隔离失败继续往下走）、`main.js:1501-1507`（只写 diag）。

**后果**：任何改动都需要跨文件跳转 + 长上下文才能确认安全 → 正是 0.3.44 那次「回调里引用了不存在的 `win`，try/catch 只包注册不包回调」能够上线的原因（CHANGELOG:84-110 自述）。

**建议**（不追求"切小文件"，按高内聚拆分）
1. 把 `startBackendWithHealing` 按阶梯级拆成 `heal/0a-structure.js`、`heal/1-entry.js`、`heal/2-profiles.js`、`heal/3-node.js`，`heal/index.js` 只保留顺序与证据判定（正好呼应 `ladder-policy.js` 已有的分级表）。
2. `main.js` 至少拆出 `boot.js`（启动编排）与 `ipc.js`（28 个 handler），主进程入口只留窗口/托盘/生命周期。
3. 空 catch 统一改成 `catch (e) { diag('…失败:', e && e.message); }`，只保留确实"绝不允许抛错"的叶子（diag-log/crash-report/lifecycle-log）。

## H-14 [P2] 桌面体验与可信度的三处缺口

| 缺口 | 证据 | 影响 |

## H-16 [P2] 零 Electron 集成测试、零 CI

**证据**
- `scripts/` 下 14 个 `test-0XX*.js` 全部是 Node 单进程脚本，覆盖纯函数与单点修复（CHANGELOG 记录了各版本断言数：046→34、047→15 等）。
- **没有任何测试真正启动 Electron 主进程**（窗口/托盘/权限/IPC/close-to-tray/quit-guard 全无自动化覆盖）。
- 仓库无 `.github/`、无 CI 配置（实测目录）。

**后果**：0.3.44 引入「点复制即崩」（`main.js:1202-1208` 自述：注册成功但回调里 `win` 未定义，异常在注册之后抛出）能在测试全绿的情况下发布，正是因为测试只覆盖注册、不覆盖回调执行。

**建议**：用 `electron --test` 或 Playwright-Electron 起一个最小 spec：①窗口能创建 ②触发一次 clipboard 权限请求不崩 ③close 事件走 showMessageBox 分支 ④28 个 IPC channel 在未授权 sender 下被拒。这四条能挡住已发生过的两类事故。
