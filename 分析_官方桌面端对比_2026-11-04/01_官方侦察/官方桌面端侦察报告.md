### 0.2 最值得注意的 5 个设计

1. **自定义协议 + 主进程反代，而不是直连本地端口**
   `dsh-app://app/` 被注册为 `standard/secure/supportFetchAPI/corsEnabled/stream/codeCache` 特权协议（`src/main.ts:188-198`）；`registerSchemesAsPrivileged` 之后由 `protocol.handle(SCHEME, …)` 分流：静态资源从 `app.asar/dsh/node_modules/@deepseek-ai/dsh-web-frontend/dist` 读（`main.ts:795`），其余全部转成 Node `fetch` 打到 Host（`main.ts:800`、`web-document.ts:97-113`）。
   后果：**渲染进程看到的是一个"本地应用源"，从不直接接触后端端口**；`set-cookie`/`content-length`/`transfer-encoding` 等响应头被显式剔除（`web-document.ts:78-82`），鉴权 cookie 由壳独占持有（`web-document.ts:104-106`）。这是官方"薄壳"安全模型的地基。

2. **Boot 数据不是内联进 HTML，而是"门闩 + IPC 注入"**
   `serveWebDocument()` 在 `index.html` 的 `<head>` 后**只**注入一行门闩：
   ```ts
   const BOOT = '<script>globalThis.__DSH_BOOT_READY__ = Promise.withResolvers()</script>'
   ```
   （`src/web-document.ts:10,31-32`）
   渲染端 `apps/web/src/main.ts:22-35` 先等 `dshDesktopBoot.ready()`，拿到 `{ injections, streamBaseUrl }` 后写入 `globalThis.__DSH_TRANSPORT__ = { ownsHost: true, streamBaseUrl }`，用 `applyIndexInjections()` 动态插 `<script>`，最后 `gate.resolve()`。
   主进程侧（`main.ts:811-816`）：
   ```ts
   ipcMain.handle(DESKTOP_IPC.boot, async (event) => {
     assertDesktopSender(event, ['app'])
     await startup
     if (backend.host === undefined || hostUrl === undefined) throw new Error('Desktop Host is unavailable')
     return { injections, streamBaseUrl: new URL(hostUrl).origin }
   })
   ```
   `injections` 由 Host 在 ready 时算好（`apps/desktop-host/src/index.ts:143`：`ctx.webServer.collectIndexInjections(ctx.connection.browserPeer)`）。
   **对比价值**：这解决了两难——静态 HTML 里没法塞"后端启动后才确定"的注入内容，又不想把渲染进程指向后端端口。

3. **进程模型：Electron 只做壳，后端是"自己 spawn 自己"的 Node 子进程**
   ```ts
   const child = spawn(this.node, [
     '--expose-internals',
     ...(this.inspectPort === undefined ? [] : [`--inspect=127.0.0.1:${String(this.inspectPort)}`]),
     entry, this.runtimeDir, this.projectDir, this.primaryRuntime ?? …,
   ], { cwd: this.projectDir, env: desktopNodeEnvironment(this.node, undefined, this.environment),
        stdio: ['ignore', 'pipe', 'pipe', 'ipc'] })
   ```
   （`src/host-process.ts:212-224`；`node` = `process.execPath`，见 `main.ts:209`）
   `desktopNodeEnvironment()` 只做一件事：`ELECTRON_RUN_AS_NODE: '1'`（`src/node-environment.ts:13-17`）。
   停机是**三阶升级**：IPC `shutdown` → 10s 未退则 `SIGTERM` → 5s 未退则 `SIGKILL` → 再 5s 不退就抛错（`host-process.ts:347-367`）。

4. **更新是"一整个已签名单元"，且强制更新策略独立于普通更新**
   - 普通更新：`electron-updater` + `generic` provider，`autoDownload=false` / `autoInstallOnAppQuit=false`（`src/update-coordinator.ts:79-80`），**下载与安装是两次独立用户批准**（`download()` 与 `install()`，`update-coordinator.ts:172-226`），安装走 `updater.quitAndInstall(true, true)`（`:218`）。
   - 轮询：基础 600s、失败指数退避到 3600s、±20% 抖动、单调时钟（`src/update-schedule.ts:19-27,93-104`）。
   - 渠道：`nightly` / `stable`，`allowDowngrade=false`，`allowPrerelease` 仅 nightly 为真（`src/updates/electron-updater/channel.ts:9-14`）。
   - 强制更新：**另一条完全独立的通道**，走自家网关 `POST /api/v0/check_client_update`（`src/mandatory-update-policy.ts:192`），可回 `40005` 表示"必须升级"（`:116`），带 `allowedPageOrigins` / `feishu-test` 鉴权 / 独立轮询与退避。
   **对比价值**：普通更新管"新版本可用"，强更管"这个版本不许再用"——两套数据面、两套 UI。

5. **安装器是自绘的原生 Win32 + GDI+ 程序，不是 electron-builder 默认 NSIS 皮肤**
   `apps/desktop/installer/window-frame.cpp`（429 行）+ `pages.nsh`（366 行）+ `drawing.nsh` / `theme.nsh` / `path.nsh` + 8 种语言 JSON（`installer/locales/*.json`）。
   同时 **`differentialPackage: true`**（`scripts/electron-builder-config.mjs:272`）——官方确实启用了差分更新包。
   安装完成页启动应用时追加 `--updated`（`installer/pages.nsh:228-230`），壳侧据此在首帧把窗口前置聚焦一次（`main.ts:422`、`main.ts:1332-1336`）。

### 0.3 与"我预期"差异最大的三点

| 预期（基于常见第三方外壳的惯性） | 官方实际 | 差异性质 |
|---|---|---|
| 桌面端会 `loadURL('http://127.0.0.1:port')`，端口随机即可 | 用 `dsh-app://` 特权协议 + 主进程 `fetch` 反代，**渲染进程完全不知道端口**（`main.ts:787-803`） | 架构级；顺带解决了 CSP/跨源/cookie 归属 |

### 2.5 CSP

**【事实】**：
- `apps/desktop` 源码内**没有**设置 `Content-Security-Policy` 响应头，也没有 `session.defaultSession.webRequest.onHeadersReceived` 注入 CSP（全目录 grep 无命中）。
- 被服务的源文件 `apps/web/index.html`（18 行）**也没有**任何 `<meta http-equiv="Content-Security-Policy">`；只有 charset / viewport / manifest / 图标 / title（`apps/web/index.html:4-12`）。
- `serveWebDocument()` 只注入一行 Boot 门闩，不注入 CSP（`web-document.ts:31-32`）。

**【推测】**（有具体候选落点）：CSP 若存在，只可能来自 Host 侧的 index 转换——`@deepseek-ai/dsh-host-webserver` 的包描述正是「HTTP and upgrade routes, **per-Peer index transform taps**, and static dist fallback」，且 `collectIndexInjections(peer)` / `renderIndex(html, peer)` 是它的公开方法（`docs/upgrade-guide/v0.2.1-rc.2/webserver-index-peer/guide.zh.md:11,15`）。
**【未证实】**：官方 CSP 指令集。→ 见 U-1。

### 2.6 其他安全细节

- **WS 反代也做了鉴权注入**：`onBeforeSendHeaders` 拦截 `ws://127.0.0.1/*`，校验 `origin === 'dsh-app://app'`，然后把 `origin` 改写为 Host origin 并注入 cookie（`main.ts:836-847`）。origin 不匹配则直接 `cancel: true`。
- **preload 的 `require` 面被压缩到 4 个模块**：
  > 「沙箱 preload 只能留下 `electron`、`events`、`timers` 与 `url`，即其 `require` polyfill 能解析的模块」——`README.zh.md#bundled-workspace-dependencies`
- **`electronFuses: { runAsNode: true }`**（`scripts/electron-builder-config.mjs:128`）。这是为 `ELECTRON_RUN_AS_NODE` 服务的必要取舍，同时也意味着**安装包里的 Electron 二进制可以被当作通用 Node 使用**——安全上是一个已知代价。

## 3. 能力域 B：桌面端与 Web UI 的关系

### 3.1 结论

桌面端**复用同一套 Web 前端构建产物**（`@deepseek-ai/dsh-web-frontend` 的 `dist`），但**加载方式与 Web 版完全不同**：

| | Web 版（`dsh web`） | 官方桌面端 |
|---|---|---|
| 页面来源 | HTTP 服务根路径 | `dsh-app://app/` ← asar 内静态文件（`main.ts:792-796`） |
| API 去向 | 同源 HTTP | 主进程 Node `fetch` 反代到 Host（`main.ts:800`） |
| Boot 注入 | 服务端渲染进 HTML | IPC 回传 + 动态 `<script>` 插入（`apps/web/src/main.ts:24-33`） |
| 鉴权 | Host 发的 cookie | 壳独占持有 cookie，页面拿不到 `set-cookie`（`web-document.ts:78-82`） |
| 端口 | 用户可感知 | 随机（`--port 0`），页面无感知 |

### 3.2 静态资源根路径

```ts
if (url.hostname === 'app') {
  if (url.pathname === '/' || url.pathname === '/index.html' || url.pathname.startsWith('/assets/')
    || ['/favicon.svg', '/manifest.webmanifest'].includes(url.pathname)) {
    return serveWebDocument(request, join(resources.dsh, 'node_modules', '@deepseek-ai', 'dsh-web-frontend', 'dist'))
  }
  if (backend.host === undefined || hostUrl === undefined || hostCookie === undefined) {
    return Promise.resolve(new Response(null, { status: 503 }))
  }
  return forwardWebRequest(request, hostUrl, hostCookie)
}
```
（`main.ts:792-801`）

**注意 503**：Host 未就绪时，非静态资源请求返回 503，而不是阻塞等待——配合前端"先渲染加载页，再等 boot"的顺序。

**`@deepseek-ai/dsh-web-frontend` 是谁**：就是 `apps/web`（`apps/web/package.json:2` 包名、`:25` `build: vite build`、`:19` `files: ["dist"]`）。即 **桌面端服务的正是 Open Web 端那份 Vite 构建产物**，没有另做一套。这意味着：Web 端任何"启动时依赖服务端注入"的改造，桌面端必须同步跟上，否则 Boot 门闩会 reject。

### 3.3 静态服务的路径穿越防护

```ts

const directory = resolve(root)
if (!target.startsWith(directory + sep)) return new Response(null, { status: 403 })
```
（`web-document.ts:23-25`）配合 `decodeURIComponent` 失败返回 400（`:22`）、非 GET/HEAD 返回 405（`:19`）。

### 3.4 内建 Web server 与端口策略

```ts
args: ['--no-open', '--host', '127.0.0.1', '--port', '0'],
```
（`apps/desktop-host/src/index.ts:36`）

- **`--port 0`** → 由操作系统分配临时端口；**`--host 127.0.0.1`** → 仅回环。即"随机高位端口 + 仅本机"。
- 端口回传给壳：`const url = ctx.connection.authenticatedUrl(\`${ctx.webServer.protocol}//127.0.0.1:${String(ctx.webServer.port)}\`)`（`index.ts:142`）。
- 壳用一次 `GET` 换取 cookie：要求 **HTTP 303 + `set-cookie`**，否则抛错：
  ```ts
  if (response.status !== 303 || cookie === null) throw new Error('Desktop Host authentication failed')
  ```
  （`web-document.ts:44-49`）
- **遗留 cookie 清理**：早期版本把 `dsh-auth-*` cookie 写进了默认 session，而 cookie 不区分端口，会在后续每个随机端口 Host 上一起发送。因此启动时主动清除：
  ```ts
  for (const { name } of await cookies.get({ url: origin })) {
  ```

| 端点 | `POST {origin}/api/v0/check_client_update` | `mandatory-update-policy.ts:192` |
| 阻止码 | `40005` | `:116` |
| 鉴权模式 | `anonymous`（正式）/ `feishu-test`（测试） | `:23,72-83` |
| 默认轮询 | `intervalMs 600_000`、`timeoutMs 15_000`、`maxBackoffMs 3_600_000`、`jitter 0.2` | `:70-72,91` |
| 重定向 | 拒绝（`redirect: 'error'`） | `:195` |
| 凭证 | 测试环境 `credentials:'include'`，正式 `'omit'` | `:195` |
| 降级链 | `base = min(maxBackoff, interval * 2**min(failures,20))` | `:218-219` |

强更**不走 electron-updater**，是壳自己轮询自家网关；`origin` 在打包期被焊进 `package.json` 的 `dshMandatoryUpdatePolicy`，**打包应用忽略运行时覆盖**（`electron-builder-config.mjs:116`、`main.ts:1497-1501`）。
强更策略**不跨重启持久化**，且强更响应**不作废也不替换**已下载的 updater 产物（`README.zh.md#mandatory-update-policy`）。

**这条设计很值得学**：普通更新是"内容分发"（可以 CDN、可以差分、可以失败重试），强更是"准入控制"（必须走可控网关、必须能秒级拉黑一个版本）。两者混在一起会互相拖累。

### 6.9 安装交接的严格性（"不清退就不许装"）

安装前必须让 Host **确认优雅停机**，否则拒绝安装：
```ts
if (requireGraceful && (!graceful || child.exitCode !== 0 || !this.shutdownCompleted)) {
  throw new DesktopHostUncleanExitError(`desktop update: Host did not complete graceful task teardown (exit …, signal …, shutdown acknowledged …, graceful deadline exceeded …)`)
}
```
（`host-process.ts:363-366`）
且 Host 必须先 `lock` 拒绝新请求、等待在途请求结束、再检查任务（`main.ts:723-730`）。
安装失败后的恢复路径：**只有确认进程已退出**才允许重新拉起替代 Host，然后重新 `navigateMain(applicationUrl)`（因为新 Host 可能有新端口/cookie/注入，`main.ts:638-653`）。

### 7.4 卸载的数据保留策略（明确且可核）

```nsis
; Electron user data and updater downloads leave with the application; the Harness home is never touched.
Function un.CleanData
  ${If} ${isUpdated}
    Return
  ${EndIf}
  ; The installer runs an older uninstaller with /KEEP_APP_DATA when replacing it from another directory.
  ${GetParameters} $R0
  ${ClearErrors}
  ${GetOptions} $R0 "/KEEP_APP_DATA" $R1
  ${IfNot} ${Errors}
    Return
  ${EndIf}

  ReadEnvStr $UnHome DSH_HOME
  …
  StrCpy $UnTarget "$APPDATA\${PRODUCT_FILENAME}"

```
（`installer/uninstall.nsh:1-27`）

删除范围（`uninstall.nsh:26-35`）：
1. `%APPDATA%\<ProductName>`
2. `%APPDATA%\<APP_PACKAGE_NAME>` + 清空父目录
3. `%LOCALAPPDATA%\<DSH_UPDATER_CACHE_NAME>`

**绝不触碰**：`~/.dsh` 或 `DSH_HOME`（会话/设置/凭据/插件）；且以 Windows 环境变量发布的 `DSH_HOME` 会保护所有与其重叠的目标。

## 12. 给 task-3 的三条提醒
