# B-04 修复方案：插件操作台账（环形日志）＋ 附进崩溃报告

> 版本 0.3.49 · 任务 task-12 · 写入域：新增 `plugin-journal.js`、`crash-report.js`
> 依据：`分析_官方桌面端对比_2026-11-04/03_对比借鉴/可借鉴清单.md` B-04（P0）
> 接线：`plugin-journal_main接线点清单.md`（交给 task-10 owner，本文不重复字段取值）

## 1. 问题本质

插件故障三次卡在同一处：**归因不到具体条目**。

- 0.3.24「清扫日志只写了数量，删的到底是谁，全靠文件时间戳反推」；
- 0.3.26 / 0.3.37 / 0.3.41 三次事故的共性是「不知道故障前一刻谁装/禁/隔离了什么」。

现有设施不解决这个：
- `lifecycle-log.js` 记的是**启动/退出**（`start()` / `exit(reason)` / `note()`）；
- `diag-log.js` 是**无结构流水**（`[时间] 插件安装结果: {spec, profile, ok, code}`）—— 要人肉从
  几十万行里捞，且和错误堆栈混在一起；
- 两者都**没有**"当初谁对哪个插件做了什么、结果如何"的结构化记录。

官方把这个能力做成环形台账（`operation-journal.ts` + `operation-history.ts`），并把最近
N 条**附进崩溃报告**（`operation-report.ts`）。本任务把这个能力搬过来。

## 2. 官方参照（逐条对齐，理由都写在代码注释里）

| 官方证据 | 本实现的落点 |
|---|---|
| `main.ts:530-532` `segmentBytes: 256*1024, recordBytes: 4096, queuedBytes: 64*1024` | `SEGMENT_BYTES=256KiB`、`RECORD_BYTES=4096`、`QUEUE_BYTES=64KiB` |
| 两段环形 | `SEGMENT_COUNT=2`：`plugin-operations-1.log`（当前）/`-2.log`（上一段），超段预算即删旧段、当前段降级、再写新段 |
| `docs/diagnostics/README.zh.md:52` 退出/恢复/安装准备最多等 **500ms** | `flush(deadlineMs)` 默认 `EXIT_FLUSH_DEADLINE_MS=500`；四路退出钩子各自用它 |
| `README.zh.md:58` 持久化失败后在**本次壳生命周期内停用**后续写入 | 写失败 → `disabled=true`，`status()` 曝光 `failed/lastError`，不再捶坏盘 |
| `operation-report.ts:36-38` 把最近操作**追加**到已写好的基础报告后，标题写明 `recent plugin operations (context, not proof of cause)` | `crash-report.js` 先写基础报告（`wx`，绝不覆盖），再 `appendFileSync` 追加该段；标题**逐字**照抄 |

| `operation-report.ts:22-61` 整个附加段 best-effort，失败时基础报告仍可用 | 追加段包 try/catch，失败只 `console.error`，基础报告字节不动 |

## 3. 设计

### 3.1 对外接口（最小面）

```js
record(entry)              // 同步入队，行级零 fs 调用；返回 false = 排队触顶已计数丢弃
recent(n)                  // 最近 n 条（旧→新），读内存环，磁盘停用也能用
renderRecent(limit)        // { lines, omitted, total, status } —— 崩溃报告用
flush(deadlineMs)          // 同步排空，崩溃/退出路径可直接等待；返回 {flushed,dropped,failed,remaining,deferred,disabled,ms}
status()                   // { dropped, droppedWritten, failed, queuedBytes, disabled, queued, written, invalidActions, recentCount, lastError, dir, limits }
journalDir() / segmentPaths()  // 排障用
```

### 3.2 记录字段（支撑归因）

一条记录 = 一行 JSON（JSONL），字段固定为白名单：

| 字段 | 例子 | 为什么需要 |
|---|---|---|
| `seq` | `42` | 单调序号：**能看出丢没丢**（序号断档） |
| `wall` | `2026-11-04T02:28:43.146Z` | 墙上时间：和用户报障时间对齐 |
| `monoMs` | `3.353` | 单调毫秒（相对进程启动）：系统改钟也不会乱序 |
| `action` | `install` / `enable` / `disable` / `uninstall` / `isolate` / `restore` / `startup-skip` | 做了什么；不认识的动作记 `unknown` 并计入 `invalidActions`（不猜、不丢） |
| `plugin` / `version` | `dsh-chrome` / `0.1.3` | 对谁做的 |
| `source` | `registry` / `local` / `profile` / `legacy` / `unknown` | 来源**类别**（不记 URL/完整路径，避免泄漏私有源） |
| `result` + `reason` | `fail` + `EISOLATE` | 结果与原因码：归因的关键 |
| `phase` | `startup` / `running` / `shutdown` / `update` | 进程阶段：区分"启动期自愈干的"与"用户手动干的" |
| `truncated` / `originalBytes` | `true` / `20181` | 这条记录不完整（被截断），且原有多大 |
| `redacted` | `true` | 凭据样式内容被打码过 |

### 3.3 环形落盘（有界内存 + 有界磁盘）

```
<logs>/plugin-operations/
    plugin-operations-1.log   当前写段（≤256KiB，超了触发滚动）
    plugin-operations-2.log   上一段（更旧；滚动时被下一个覆盖）
```

- 追加前查段大小，超 `SEGMENT_BYTES` → 删 `-2`、`-1`→`-2`、下一条写入新建的 `-1`；
- 单次 append 按 `CHUNK_BYTES=16KiB` 分块，避免一次写几百 KiB 卡事件循环；
- 队列 `QUEUE_BYTES=64KiB` 是**内存**边界：触顶时**丢弃新到达的记录并计数**。

### 3.4 截断与「不假装完整」

单条 ≤4 KiB 有两条路径，都会留下标记：
1. **字段级**：`plugin≤200` / `version≤64` / `reason≤120` 字符，一旦被剪 → `truncated:true` +
   `originalBytes`（未剪前的 JSON 字节数）；
2. **整条兜底**：若序列化后仍 >4 KiB，逐级降级（丢 `reason` → 剪 `plugin`/`version` → 只留
   归因必需字段并逐步截短插件名），同样带 `truncated/originalBytes`。

凭据样式（`token=`/`password:`/`bearer …`/`api_key=`）一律打码 `***` 并标 `redacted:true` ——
读者必须能看出"这条不是调用方原样给的"。

### 3.5 背压与「禁止静默丢弃」

- 触顶：`record()` 返回 `false`，`dropped += 1`，记录**仍进内存环**（崩溃报告还能看到，标
  `persisted:false` 显示「(未落盘)」）；
- 下一次 `flush()` 先写一条 `action:"journal-drop"` 的说明记录（含精确条数、当时排队字节），
  再写一条**诊断日志正文**（`插件台账：排队触顶丢弃 N 条…`）—— 两个地方都能搜到；
- `status().dropped` / `droppedWritten` 双计数，说明行不会重复刷。

### 3.6 写失败降级（可见，不假装成功）

任何 `mkdir/append/rotate` 失败 → `failed += 1`、`lastError`、`disabled = true`，并停止后续
落盘尝试（官方语义：别反复捶一个坏盘）；`stderr` 打一行 `[plugin-journal] …`。
内存环照常维护 → 崩溃报告里的插件段仍然有内容，并额外标注
`[ledger degraded] 台账落盘已停用：…（以上内容来自内存环形缓冲）`。

### 3.7 与阶段一 diag-log 分层的对齐

| 写入 | 层 | 理由 |
|---|---|---|
| `record()` 入队 | **零 IO**（与 `diag-log.write()` 同纪律） | 插件操作在主进程热路径上，不能同步写盘 |
| 定时落盘（1s） | 批量层 | 台账记录稀疏，1s 足够；不像 diag 那样每 200ms 必刷 |
| `flush(deadlineMs)` | 同步、可等待 | 崩溃路径（`crash-report`）与退出钩子必须"等得到" |
| `isolate`/`restore` **失败** | 额外镜像到 `diag-log.writeDurable()` | 低频且正是事故现场：这一条要在主日志/错误清单/桌面报告里"返回即可读"。高频的 install/enable **绝不**走同步写（否则把 H-10 的收益吐回去） |

### 3.8 退出覆盖（不假设钩子一定跑）

四路钩子（`process 'exit'`、包装 `app.exit`、`app 'will-quit'`、包装 `process.exit`），用
`Symbol.for('dsh.exitFlushHooks')` 独立注册表；与 diag-log 的包装形成链式调用，互不覆盖。
另外 `crash-report` 在自己的写盘路径里显式 `flush(300ms)` —— 崩溃现场不依赖任何钩子。

### 3.9 崩溃报告集成（追加，不重写）

```
===== DSH Desktop 崩溃报告 … =====        ← 基础报告（wx 写，字节永不重写）
----- error -----
----- backend log tail -----
----- renderer console (error level, oldest first) -----
----- recent plugin operations (context, not proof of cause) -----   ← 0.3.49 新增（追加）
#1 … install dsh-chrome@0.1.3 source=registry ok phase=startup
…
…（省略 N 条更早记录，完整台账见 <dir>）
[collection complete] records=N dropped=D ledger=<dir>
[ledger degraded] …（仅当落盘停用）
```

「context, not proof of cause」是**契约**，不是修饰：它明确这段不构成因果证据，不得据此宣称
某插件导致了崩溃，也**不得**喂给 `ladder-policy.js` 的 needs-proof 判定。

## 4. 安全与隐私（B-04 明确点名）

1. **只记白名单字段**：接线方传 `{...token:'x'}` 这类字段会被直接丢弃（测试 ⑥ 断言报告里
   连 `"token"` 键名都不出现）；
2. **不记 spec 原文 / 命令行 / 插件 stdout**：spec 可能含私有 registry 地址，插件 stderr 可能
   含凭据（官方 `host-process.ts:364` 同纪律）；`source` 只记类别；
3. 字符串再兜一层凭据样式打码 + `redacted` 标记；
4. 单行 JSON（换行/控制字符被压成空格），不会伪造出"另一条记录"。

## 5. 明确不做（避免越界/过度设计）

- **不接线**：`main.js` 的调用点由 task-10 owner 按 `plugin-journal_main接线点清单.md` 落；
  本模块在无接线时也能被单测直接驱动（本次 54 项单测即如此）；
- **不喂自愈阶梯**：台账是上下文，`ladder-policy` 的 needs-proof 判定不读它；
- **不打包诊断包**（B-03 的范围）：台账文件落位已经能被打包逻辑直接收；
- **不轮转清理历史段**：2 段环形本身就是上限（不需要额外清理策略，避免重犯 H-09 的 `.bak` 堆积）。
