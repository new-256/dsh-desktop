## 1. 残余风险

### R-1【需接线·高】B-03 节拍器已就绪，但 main.js 还在用旧的两行定时器
`createBackendUpdateLoop()` 已导出并单测通过，但 `main.js` 仍是
`setTimeout(() => checkBackendUpdates(), 5000)` + `setInterval(..., 6 * 3600 * 1000)`。
**在接线之前，退避/抖动/单飞在真实应用里不生效**（只有单测证明它们是对的）。
接线成本：删两行、加两行。建议与阶段二 main.js 团队一起收尾时完成。

### R-2【需接线·中】B-06 的确认令牌没人签发
`issueUpdateConfirmation()` / `stageDsh(cb, version, {confirmation})` 已就绪，`assertConfirmationFresh` 在
无令牌时显式记 `unbound` 日志后**继续**（不能因为 main.js 没接线就把更新功能弄挂）。
⇒ 当前实际防护等级是"**有记录、无拦截**"。接线点：设置窗弹确认框前取令牌、
`settings:download-updates` 回调里带回。建议同 R-1 一并做。

### R-3【需接线·中】B-08 的 `blocked` 返回值没人消费
`applyStaged()` 被阻止时返回 `{blocked:true, retryHint, nextRetryAtMs}`，`main.js:3272` 只把它写进
`diag(...)`，用户看不到"正在收尾，稍后自动重试"。
缓解事实：启动链第 3 步调用时后端**本来就没在跑**，闸门实际不会在那里拦；真正的拦截发生在
"后端运行中改设置/换版本"这条路径上（阶段二 main.js 侧）。仍建议补一句 `pushLog`。

### R-4【范围·中】B-17 只覆盖"我们亲手下载的那一段"
三段实际情况：
1. **dsh 后端包**：已全覆盖（tarball 先下载、先校验、再从本地 tgz 安装）。
2. **Node 包**：已覆盖（`SHASUMS256.txt` 精确匹配）。
3. **依赖树**：`@deepseek-ai/dsh` 的依赖仍由 npm 自己校验（npm 会核 packument 的 integrity）——
   这部分我们**没有**再做一次独立校验，属于"信任 npm 的校验结论"。
⇒ 不要对外宣称"整棵安装树的每个字节都经我们校验"。这条边界已写进修复方案第 2.3 节。

### R-5【行为变更·中】安装方式从"按版本号装"改成"按已校验 tarball 装"
影响面：
- npm 会把依赖写成 `file:<绝对路径>`，我在装完后立即改写回版本形态；若改写失败（磁盘满/占用），
  暂存树的 package.json 会留一个指向 `downloads/` 的路径 —— 该路径下次启动就不存在了。
  **影响有限**（`dshVersion()` / `stagedVersions()` 只读 `node_modules/@deepseek-ai/dsh/package.json`，
  不读暂存树的根 package.json），但不够干净。【未验证】真实 npm 版本（11.19.0 已实测可通过）之外的行为。
- `--no-package-lock` 是刻意加的（避免 lock 里出现 `file:` 路径），这意味着依赖解析**不受 lock 约束**，
  与旧实现一致（旧实现也没有 lock）。
- 回滚方式：把 `installStagedDsh` 的 target 从 `tgz` 改回 `@deepseek-ai/dsh@<version>` 即可，其余不动。

### R-6【策略冲突·中】"缺哈希默认继续"与用户规则「禁降级兜底」的张力
B-17 官方验收第 4 条要求"无哈希可用时不能把用户卡死"，而项目规则要求"开发期禁止自动降级"。
我的处置：**默认不阻断，但四处留痕**（`logDurable` + journal `ERR_UPDATER_INTEGRITY_METADATA_MISSING` +
用户可见文案 + 返回值 `integrity.missingMetadata`），并给 `DSH_REQUIRE_INTEGRITY=1` 硬开关。
⇒ 这不是"静默兜底"，是"显式降级"。若 lead 认为应当默认严格，改一个默认值即可（`integrityPolicy` 单点）。

### R-7【未验证·中】真机断电/强杀下的 B-08 / copy 路径行为
"后端仍在运行"用**注入探针**与**真实占用句柄**验证；但"后端刚被 taskkill、文件句柄尚未释放"这种
真实竞态窗口没有在真机上复现过。`scanBackendProcesses()` 用 `Get-CimInstance` 查 PID，本身有
几百毫秒延迟 —— 在"刚刚退出"的瞬间可能仍看到进程。【未验证】该窗口内 applyStaged 是否会被误拦
（误拦的后果是"下次启动再装"，属安全侧，不丢数据）。

### R-8【探测成本·低】`scanBackendProcesses()` 会起一个 pwsh
只在"确有暂存更新"时调用（无暂存直接 return，启动常态零成本）。但若某次暂存长期无法应用，
每次启动都会付一次 ~300-800ms 探测。可接受，记录在此。

### R-9【台账·低】`rolled-back` 是新增的 journal 状态
`journalUnverified()`（只认 `applied`）与 `journalMarkVerified()`（只改 `applied`）都不受影响，
`main.js` 也没有枚举全部状态。但**其他读 journal 的地方**（诊断包导出、设置窗"更新历史"若有）
需要知道新状态，否则会把它当成未知值显示。已在导出符号注释里写清。

### R-10【口径·低】`dsh.new.invalid.json` 是一个新的状态文件
新增一个 root 级 JSON。风险：用户看到它不知道是什么；诊断包里有它时要能解释。
处置：文件名自解释 + `logDurable` 明确写"已把 dsh.new 标记为不可应用"，且能清干净时自动删除。
【建议】阶段二诊断包导出（B-13）把它列进清单。

### R-11【未验证·低】`dshDistMeta` 的"缓存优先"策略会掩盖上游重发
`lastDshDist` 来自最近一次 packument；如果上游在我们检查后立刻重发同版本，**在同一个进程内**
缓存不会刷新，直到下一次 `checkForUpdates`。这不是漏洞（下次检查会刷新并让确认过期），
但意味着"重发检测"的时效等于"检查节拍"。【未验证】npm registry 对同版本重发是否真的允许
（多数 registry 禁止覆盖已发布版本，这条防线可能长期处于"不会触发"状态 —— 属于廉价保险）。

## 3. 调试中修正过的两处实现（留下的记录）

1. **`msUntilDue` 的取整**：最初用 `floor(remain/1e6)+1`，导致"恰好 600000ms"变成 600001ms，
   测出定时器早醒 1ms。改成向上取整 `(remain+999999n)/1000000n`。这类 1ms 偏差在 600s 尺度无害，
   但会让"精确序列"断言变得不可信，故修正实现而不是放宽断言。
2. **copy 兜底后暂存树删不净**：最初想把它"改名藏起来"，实测发现**占用在 dsh.new 内部时连
   rename dsh.new 本身都 EPERM**，改名方案在它唯一需要的场景下失效。改为 dsh.new **外部**标记
   （`dsh.new.invalid.json`），并让 `applyStaged` / `stagedVersions` 统一认它。
   **这是本轮最有价值的一次"真验证推翻设计"**：只跑 happy path 的话，这个隐患会留到线上。
