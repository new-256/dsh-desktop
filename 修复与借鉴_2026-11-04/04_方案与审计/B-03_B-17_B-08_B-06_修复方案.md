## 一、B-03 更新轮询工程化 → 新文件 `update-schedule.js`

### 1. 问题

旧实现（`main.js` 原 `scheduleSilentUpdates`）：`setTimeout(check, 5000)` + `setInterval(check, 6h)`。四个缺陷叠在一起：

| 缺陷 | 用户可感知表现 |
|---|---|
| 固定节拍、失败不退避 | 弱网/机场/公司代理下每次都在同一时刻硬撞镜像；恢复后也要等满 6 小时 |
| `Date.now()` 语义 | NTP 校时/改时区会让间隔算错（甚至一次连查多次） |
| 无抖动 | 所有机器同时装好 → 同一秒一起请求，镜像侧是整齐尖峰 |
| 无单飞 | `setInterval` 不看在途请求，慢请求会叠起来连发 |

### 2. 方案：纯逻辑 + 依赖注入

`update-schedule.js` 只做"何时检查"，不碰"检查到之后做什么"。时钟/随机源/定时器/检查函数**全部可注入**，所以测试用假时钟推进即可断言精确序列，不需要真等 600 秒。

```
createUpdateScheduler({check, hrtime?, random?, setTimeoutFn?, clearTimeoutFn?, baseMs?, maxBackoffMs?, jitter?, log?})
  ├─ start() / stop()              常驻节拍（生产路径）
  ├─ runCheck(reason)              单飞执行一次；进行中则并入在途 promise（joined=true）
  ├─ isDue(now?) / msUntilDue(now?) 到期判定（单调 tick 为准）
  └─ status()                      {baseMs, currentBaseDelayMs, failures, counters, dueAtTick, ...}
```

六条要求逐条落地：

| 要求 | 实现 |
|---|---|
| 单调时钟 | 默认 `() => process.hrtime.bigint()`；**全模块零 `Date.now()`**（测试把 `Date.now` 换成"被调用就抛错"，节拍器照常运行） |
| 完成起算 | 到期时刻 = `lastCompletedNs + jitteredDelay`（在 `finally` 里以**结束时刻**为基准），慢请求不连发 |
| 指数退避 | 初始 = base(600s)；每次失败 `min(max, delay*2)` ⇒ **1200s → 2400s → 3600s（封顶）**；成功立刻回 600s |
| ±20% 抖动 | `lower=max(1000, d*(1-j))`、`upper=min(max, d*(1+j))`、`round(lower+(upper-lower)*random())`（与官方 `:94-96` 逐字同口径；**封顶处抖动是单边的**，如实保留官方语义） |
| 单飞 | 在途时第二次触发只 `await` 同一个 promise，`joined=true`、`counters.joined++`，日志留痕 |
| 环境变量 + 非法即抛 | `configFromEnv({DSH_UPDATE_BASE_MS, DSH_UPDATE_MAX_MS})`：非纯整数（如 `60s`）/ `max<base` / `jitter∉[0,1)` 一律 `RangeError`，**不静默纠正** |

### 3. 接线

`updater-backend.js` 新增 `createBackendUpdateLoop(opts)`（`:5262`）：把 `update-schedule` 的 `check` 接到 `checkForUpdates({includeNode})`，并把「检查有失败项」也判为失败（否则弱网永远按基础节拍硬撞）。

**main.js 需要一行接线**（本团队写入域不含 main.js）：
```js
const loop = mgr.createBackendUpdateLoop();   // 取代 setTimeout(5s) + setInterval(6h)
loop.start();
```

```

```
实测退避序列（`jitter: 0`，假时钟推进，**零真实等待**）：**`[1200000, 2400000, 3600000, 3600000]` ms**，成功一次后回到 `600000`。

## 二、B-17 运行期完整性校验

### 1. 问题

构建期我们对 vendor 分卷逐个核 sha256（`scripts/write-vendor-manifest.js`），**运行期**从 registry/镜像下载的后端包却只查 `content-length`。镜像同步到一半、CDN 截断、代理注入内容时，会把坏树装进 `dsh.new` 并在下次启动"应用"它 —— 归因难度远高于下载那一刻。

### 2. 方案

| 符号 | 行 | 作用 |
|---|---|---|
| `parseSri` | `:684` | 解析 SRI（多条目时**按最强算法**取，sha1 写在前面也不降级） |
| `chooseIntegrity` | `:703` | `dist.integrity`(sha512/384/256/1) 优先 → 退 `dist.shasum`(sha1 hex) → 都没有 = null |
| `digestFileSync` | `:712` | 流式摘要（不整读进内存），给 base64/hex 两种表示 |
| `verifyFileIntegrity` | `:736` | 四条出口：通过 / 摘要不匹配 / **大小不符（截断）** / 缺元数据 |
| `integrityPolicy` | `:4264` | 纯策略函数：`accept` / `accept-unverified` / `reject` + 错误码 |
| `downloadVerifiedDshTarball` | `:4285` | 下载 → 校验 → 按策略放行或**删包中止** |
| `installStagedDsh` | `:4319` | 已校验的本地 tgz → `npm install <tgz>`（install 前不建 dsh.new，失败即保留旧版） |
| `verifyNodeZip` | `:4473` | 第二消费者：`SHASUMS256.txt` 逐行精确匹配 `node-v<ver>-win-x64.zip` |

关键设计：
- **先校验、后动磁盘**：`dsh.new` 只在安装阶段才创建 ⇒ 校验失败时"保留旧版"不靠回滚，而是**从未动过**。
- **安装包也换了来源**：`npm install @deepseek-ai/dsh@<v>` → `npm install <已校验的 tgz>`。否则我们校验的是一份、npm 装的可能是另一份（两次下载）。装完把 `file:` 依赖声明改回版本形态，暂存树里不留临时路径。
- **缺哈希 ≠ 通过**：`verifyFileIntegrity` 返回 `missingMetadata:true`（`ok:false`），策略默认"记账后继续"（官方 B-17 验收第 4 条：无哈希可用时不能把用户卡死），`DSH_REQUIRE_INTEGRITY=1` 则一律拒绝。
- 校验失败的错误码进入 journal 白名单：`ERR_UPDATER_CHECKSUM_MISMATCH` / `ERR_UPDATER_INTEGRITY_METADATA_MISSING`（对齐官方 `update-journal.ts:12-13` 把"校验和不匹配"当一等公民错误）。

### 3. 边界（诚实标注）

本项防的是**传输损坏/截断/部分篡改**。它**防不了**"镜像站被整体接管"（元数据与 tarball 会一起被改）—— 那需要签名信任根（B-10 的资金问题）。**不宣传成"供应链安全已解决"。**

### 4. 验证证据（`scripts/test-b17-integrity.js`，40 断言全绿）

```
结果：40 通过 / 0 失败（耗时 142ms）
```

| 路径 | 结论 |
|---|---|
| 正常 | sha512 一致 → `ok=true`，`algo=sha512`、`from=dist.integrity`、策略 `accept`；只有 shasum 时退 sha1 且通过；多条目 SRI 选最强 |
| 篡改（改 1 字节） | `ok=false`，原因写"校验不匹配"（不是"下载失败"），策略 `reject` + `ERR_UPDATER_CHECKSUM_MISMATCH` |
| 截断（短 1 字节） | 有 content-length 时先报 `truncated=true` "大小不符（可能被截断）"；无大小信息时按摘要不匹配归因；同样 `reject` |
| 缺元数据 | `ok=false` + `missingMetadata=true` + 明确原因；默认 `accept-unverified`（记账继续）、`requireHash:true` → `reject`(`ERR_UPDATER_INTEGRITY_METADATA_MISSING`) |

## 三、B-08 干净退出才允许应用更新 + 回滚接电

### 1. 干净退出闸门

官方判定式是"子进程已退出 + 退出码 0 + teardown 完成"。我们在 Windows 上已实测 SIGTERM handler 不触发（0.3.44），**不能照抄**；等价物只能是"后端进程真的不在了"。因此：

```
applyStaged(options)
 ├─ 无暂存内容 → 直接返回（**不探测**：启动常态零开销）
 ├─ 有暂存 → applyGateStatus()
 │    ├─ 主进程探针 setApplyGate(() => ({backendRunning, pendingWrites}))  ← 有就用它
 │    └─ 否则自带进程探针 scanBackendProcesses()：按**专用** backend\node.exe 精确匹配 PID
 │         （探针自身失败 ⇒ 判"不干净"，绝不带着未知状态改磁盘）
 ├─ 不干净 → **不应用**：dsh.new/node.new 原样保留 + journal ERR_UPDATER_BACKEND_NOT_STOPPED
 │            + 返回 { blocked:true, gate, retryHint:"正在收尾，稍后自动重试…", nextRetryAtMs }
 └─ 干净 → 走原有应用流程
```

**不许强杀后硬上**：检测不通过就返回 blocked，绝无 taskkill-然后-继续的路径。

### 2. 回滚接电（与阶段一 H-01 联动）

`rollbackDsh()`（`:4723`）补三件事，全部 `logDurable`：

1. **journal 对齐**（`journalMarkRolledBack`，`:4754`）：把坏版本那条 `applied` 改写成 `rolled-back`，并补一条 `rolled-back` 结论。
   *为什么必须*：不改的话，回滚后只要有一次启动成功，`journalMarkVerified()` 就会把**坏版本**标成 verified，台账从此撒谎；而后续自动回滚决策又以 journal 为依据 —— 这就是"回滚回坏版本"的成因。
2. **versions.json 重写**（原有，保留）。
3. **清掉 H-05 中断标记**：回滚是对"应用被打断"的最终处置，标记必须结束，否则下次启动还会再报一次中断。

### 3. 阶段一遗留：`swapDshByCopy` 现在产 `dsh.previous`

旧实现 `copyDir(dshNew → dsh)` + 删 `dsh.new`，两个缺陷：①**叠加覆盖**（新版删掉的文件作为旧版残留留下，形成混合树）；②**不产 `dsh.previous`** ⇒ H-01 在这条路径上"无版本可退"。

新实现（`:4890`）：`dsh.new → dsh.copy`（同卷临时）→ 校验树完整且版本正确 → 才 `dsh → dsh.old` → `dsh.copy → dsh` → `dsh.old → dsh.previous`。任何一步失败都把 dsh 还原原位、保留 dsh.new，绝不留下"dsh 不存在"的中间态。

**顺带发现并处理的真实隐患**：当占用在 `dsh.new` **内部**时，交换成功后 `dsh.new` 删不净，而且**连 rename `dsh.new` 本身都 EPERM**（实测）。若不处理，下次启动会把一棵缺文件的暂存树当待装版本再换一次 → 把好树换坏。因此标记放在 dsh.new **外面**：`root/dsh.new.invalid.json`，`applyStaged` / `stagedVersions()` 统一认它，能清干净时自动清除。

### 4. 验证证据（`scripts/test-b08-b06-revision.js` 中的 B-08 段）

- 无暂存 → `{dsh:null,node:null}`，探针函数**未被调用**（用"被调用就抛错"的探针验证）。
- `backendRunning:true` → `blocked:true`、原因含"后端进程仍在运行"、`retryHint` 含"正在收尾，稍后自动重试"、活跃版本未变、`dsh.new` 原样、journal 落码。
- `pendingWrites:3` → `blocked:true`、原因含"3 项会话写入未落盘"。
- 探针干净 → `clean:true`（自带进程探针在无后端进程时同样返回可判定布尔）。
- 副本兜底实测（真实占用句柄锁 dsh.new）：`applied.dsh=0.4.1`、**`dsh.previous=0.4.0`（已产出回滚素材）**、无 `dsh.old`/`dsh.copy` 残留、`dsh.new.invalid.json` 已落、`stagedVersions().dsh===null`、**再次 applyStaged 不再二次交换**（活跃版本与回滚素材均未被破坏）。
- 回滚实测：`rollbackDsh()===true`、活跃版本回到 0.4.9、`dsh.previous` 被消费、`versions.json` 重写、`journalUnverified()` 归零、`rolled-back` 记录写明 `0.5.0 → 0.4.9`、中断标记清除且不再报中断；无回滚目标时返回 `false` 且不动活跃版本。

## 四、B-06 更新确认与版本绑定（revision + 内容摘要）

### 1. 问题

弹窗说「有新版本 vX」，用户点确认后到真正下载之间，目标可能已变：上游把**同一版本号**重发了一份新 tarball，或用户在设置窗切了更新路线/换了版本。旧实现没有任何代号，确认会按"它记住的版本号"继续执行 ⇒ "确认的是 A，装上去的是 B 的内容"。

### 2. 方案

```
revision（单调代次，只有 bumpUpdateRevision 能改）
  ├─ 触发点：writeSettings 命中 TARGET_KEYS(npmRegistry/nodeDist/updateChannel/channel/dshVersion)
  │           + stageDsh 显式换后端版本成功 + stageNode 显式换 Node 版本成功
  └─ 每次自增同时清空候选快照（旧令牌连重新签发都不可能）

确认令牌 = { revision, version, digest }
  digest = sha256(规范 JSON{version, tarball, integrity, shasum})   ← 绑定**内容**，不绑"最新"
```

三段校验，位置可解释：

| 阶段 | 函数 | 时机 | 抓什么 |
|---|---|---|---|
| 一 | `assertConfirmationFresh` | `stageDsh` **最前**（任何网络请求之前） | 代次变了 / 令牌版本 ≠ 本次目标 / 快照缺失 |
| 二 | `assertConfirmationFresh`（目标解析后） | 拿到 `latest` 后 | 令牌版本 vs 实际候选 |
| 三 | `checkConfirmationDigest` | 拿到 registry `dist` 元数据后、下载前 | **上游重发同版本**（内容摘要变化） |

失败即 `ERR_UPDATER_CONFIRMATION_STALE` + 可操作文案「目标已变更，请重新确认」。未携带令牌时**显式记日志**（`unbound`），不假装校验过。

### 3. 验证证据（同脚本 B-06 段）

- 代次：切路线自增；重复写同值**不自增**；写无关设置**不自增**。
- 令牌内容来自快照（revision/version/digest 三者一致）；新鲜令牌通过。
- 上游重发（integrity 改一个字符）→ 摘要不一致 → 拒绝，文案指明"上游重发"。
- 切渠道（`bumpUpdateRevision`）→ 旧令牌作废、快照清空（`issueUpdateConfirmation()` 返回 null）。
- 目标版本不一致 → 作废；未携带令牌 → `unbound:true` 且 `ok:true`。
- **端到端**：把 `DSH_NPM_REGISTRY` 指向不可达地址 `https://127.0.0.1:1/registry`，用过期令牌调 `stageDsh` → 毫秒级（实测 8ms）抛"目标已变更"，错误串里**没有任何网络错误** ⇒ 证明拒绝发生在网络之前；journal 落 `ERR_UPDATER_CONFIRMATION_STALE`。
