## 0. 一句话结论

四条缺陷的共同症状是**「用户看到的现象」与「系统真实状态」脱钩**：启动挂了却没有任何提示（H-02/H-03）、更新装坏了却拿不到现成的回滚（H-01）、唯一的通知通道可能被系统静默吞掉（H-08）。本次修复的原则是**把静默变成可读、把死代码变成可点的动作、把不可观测变成可取证**，并且在结构上不再往 2900 行的 `main.js` 里塞判断逻辑 —— 所有判定进入新模块 `startup-deadline.js`（纯函数、不 require electron、可在 Node 里直接单测）。

## 1. 结构决策：为什么新增 `startup-deadline.js` 而不是就地改 `main.js`

`PROJECT_RULES.md §3` 明确：`main.js`/`updater-backend.js` 本次阶段不得继续就地膨胀，新增逻辑一律落到新文件，由现有文件以单行 `require` + 少量调用接入。

因此本方案把**判断**与**执行**切开：

```
startup-deadline.js（纯逻辑，无 electron，可直接单测）
├─ §1 启动截止时间
│   ├─ resolveBudgets(env)          预算解析 + 非法环境变量上报（不静默容忍）
│   ├─ createTrace({now})           阶段打点（ready→seeded→…→loaded）
│   ├─ createWatchdog({…})          注入式计时器（生产传 setTimeout，测试传假计时器）
│   ├─ buildTimeoutReport({…})      把现场证据组装成结构化报告
│   ├─ formatTimeoutMessage({…})    超时文案（阶段名 + 最后一条日志 + 日志绝对路径）
│   ├─ createTimeoutError(report)   Error 携带 code/phase/report（沿既有错误通道走）
│   └─ lastMeaningfulLogLine(…)     "最后一条日志"的正确取法
└─ §2 启动恢复决策（H-01）
    ├─ createGuardState / normalizeGuardState   失败计数台账（落盘 JSON，容忍坏字段）
    ├─ bumpFailure / resetOnHealthyBoot         连续失败计数 / 成功清零
    ├─ recordRollback / stashNotice / clearNotice  回滚留痕 + 一次性提示
    ├─ decideRecovery({…})                       ★ 自动回滚的唯一准入判定（含防死循环）
    ├─ formatJournalEvidence(…)                  journal 证据的人话化
    └─ formatRollbackNotice(…)                   "已自动回滚到 vX" 的提示文案
```

`main.js` 只做接线：读/写台账、调 `mgr.rollbackDsh()`、弹窗/通知、启停 watchdog。

## 2. H-02（P0）`spawnBackend` 的 async executor 反模式

### 2.1 缺陷机制（复述，用于对齐）

```js
function spawnBackend() {
  return new Promise(async (resolve, reject) => {   // ← executor 是 async
    const env = mgr.buildDedicatedEnv();            // ← 同步可抛（mkdirSync）
    const child = spawn(p.nodeExe, args, { … });    // ← 同步可抛（EACCES/EPERM）
```
async 函数体内同步抛出只 reject **该 async 函数自己返回、随后被丢弃**的 Promise；外层 `new Promise` 永不 settle → `await startBackendWithPluginIsolation()` 永不返回 → `whenReady` 的 `catch → showFatal(err)` 永不执行。用户看到的是启动画面永久旋转，且日志里没有失败记录。

### 2.2 改法：同步准备 + 显式 reject + 监听注册也包进 try

1. 抽出 **普通（非 async）函数** `prepareBackendSpawn()`：路径校验 → `buildDedicatedEnv()` → `spawn()`，原样保留原有注释与参数（`--max-http-header-size=1048576` 等）。
2. `spawnBackend()` 的 executor 变成**同步函数**：
   ```js
   return new Promise((resolve, reject) => {
     let prepared;
     try { prepared = prepareBackendSpawn(); }
     catch (err) { diag('后端进程准备失败（同步阶段，已显式 reject 外层）:', …); reject(err); return; }
     …
     try { /* stdout/stderr/error/exit 监听注册 + deadline 装配 */ }
     catch (err) { killProcessTree(child); settle(reject, err); }
   });
   ```
3. 统一 `settle(fn, value)` 收敛（含 `settled` 幂等 + 停表），杜绝"多路径重复 resolve/reject"。
4. 错误文案语义**逐字保留**（`缺少 Node 运行时：…`、`后端进程提前退出（code=…）`）。

## 3. H-03（P0）全链路启动超时（分阶段，不是一刀切）

### 3.1 为什么分三段

三个阶段的故障含义完全不同，合成一个总数就再也回答不了"到底哪一步挂了"：

| 阶段 | 覆盖范围 | 默认预算 | 错误码 | 给这个数字的理由 |
|---|---|---|---|---|
| `spawn` | spawn 到 `dsh web: <url>` 被抓到 | **120s** | `E_STARTUP_SPAWN_NO_URL` | 冷启动含 node 24 引导 + `dsh web` 初始化 + 插件激活；本机正常 6~12s，慢盘/杀软全盘扫描可到 40s+。120s ≈ 10 倍余量 —— 超过这个量级就不是"慢"，而是在"等"（等文件锁/网络/stdin） |
| `health` | 地址已打印 → HTTP 首次成功响应 | **60s** | `E_STARTUP_HEALTH_UNRESPONSIVE` | **沿用既有 `waitForServer(url, 60000)` 的数字**（不是新造的）：地址打印后 HTTP 通常 <1s 可用 |
| `paint` | 主窗口 `did-finish-load` | **60s** | `E_STARTUP_PAINT_STALLED` | 只加载本机 `127.0.0.1`，正常 <2s；`did-fail-load` 另自带 5 次指数重试（≈15s）。60s 只兜"既不完成也不报错"的白窗 |

### 3.2 环境变量覆盖

```
DSH_STARTUP_TIMEOUT_SPAWN_MS / _HEALTH_MS / _PAINT_MS    单阶段覆盖（正数毫秒）
DSH_STARTUP_TIMEOUT_SCALE                                全局倍率（作用于默认值与显式值）
```
非法值**不静默容忍**：`resolveBudgets()` 返回 `errors[]`，`main.js` 把每条写进诊断日志 + 后端日志。理由 —— 否则"我明明设了 300s，怎么 120s 就超时"会变成一个查不出来的谜。

### 3.3 超时之后做什么（不是吞错误）

- `spawn` 超时：先 `killProcessTree(child)`（卡住的后端占着端口/文件锁，不清掉会让下一级自愈重试一起失败），再 `reject(typedError)`。
- `health` 超时：同上，且错误码与 spawn 不同（H-03 明确要求区分"未捕获到地址"与"地址已打印但无响应"）。
- `paint` 超时：**不杀后端**（HTTP 已就绪，后端是好的），直接 `showFatal(err)`，弹窗里说明"卡住的是主窗口加载"。
- 三条路径最终都汇聚到**既有** `showFatal()`；超时文案包含**超时阶段名 + 最后一条后端日志 + 日志绝对路径**（硬性三项），另附阶段打点序列。

### 3.4 明确不做的事

`ensureSeeded()`（payload 解压）是**同步**的，主进程在它执行期间被阻塞 —— 计时器根本不会跑。所以**不**给同步阶段假装设超时（写出来只会误导排查者）。这一点在 `main.js` 的注释里写明了。

## 4. H-01（P0）让回滚真正接电

### 4.1 三处改动

1. **故障弹窗加回滚按钮**：`showFatal()` 的按钮从"硬编码 6 个 + `switch(r.response)`"改成**动作表**（`[{label, run}]`），加减按钮不会把动作错位（0.3.44「注册与回调不一致」的同类风险）。当 `dsh.previous` 可用且判定"值得回滚"时，按钮出现在**第一位**（`defaultId=0`），点击 → `performRollback('manual')` → `restartApp()`。
2. **连续 2 次启动失败 → 自动回滚一次**（`FAILURE_THRESHOLD=2`）：失败计数**落盘**到 `%APPDATA%\DSH Desktop\startup-recovery.json`（内存计数在两次启动之间会归零，等于永不触发）。启动成功后 `resetOnHealthyBoot()` 清零。
3. **`journalUnverified()` 从"只写日志"升级为决策输入**：
   - 失败时：作为 `decideRecovery()` 的证据 → 给出"上次更新未验证通过"的标题、把回滚设为推荐项、把 journal 明细写进弹窗 detail；
   - 成功时：启动完成后**非阻塞**提示一次（含"回滚到上一个版本"按钮），而不是静默写一行日志。

### 4.2 防死循环（这是"不做降级兜底"的边界）

```js
AUTO_ROLLBACK_LIMIT = 1     // 本轮只允许自动回滚 1 次
```
`decideRecovery()` 的判定顺序（先否决、后准入）：

| # | 条件 | 结果 | 为什么 |
|---|---|---|---|
| 1 | `fatalKind === 'address-in-use'` | `none` | 另一个实例还在跑，回滚治不了端口冲突 |
| 2 | 没有可用的 `dsh.previous` | `none` | 无米下锅，不给必然失败的动作 |
| 3 | `rollbacksInChain >= 1` | `none` + 推荐手动 | 再自动回滚会把磁盘上仅剩的旧版本也消费掉，并把用户送进"重启—回滚"死循环 |
| 4 | `consecutiveFailures >= 2` | **`auto-rollback`** | H-01 的要求 |
| 5 | journal 有未验证记录 | `advisory` + 推荐手动 | 当前版本本身可疑 |
| 6 | 其它 | `none` | 走既有恢复弹窗 |

自动回滚成功后的"已自动回滚到 vX"提示**活不过重启**，因此暂存进台账（`pendingNotice`），由下一次启动读出后**非阻塞**显示一次并清空。

### 4.3 可逆性与留痕

`rollbackDsh()` 是**不可逆**动作（当前 dsh 目录改名 `dsh.failed` 后删除，只把 `dsh.previous` 换回来），因此每次执行都必须：
- 诊断日志：`回滚（auto|manual）完成：<from> → <to>`；
- 生命周期台账：`lifecycle.note('auto-rollback' | 'manual-rollback', {from,to,…})`；
- 恢复台账：`lastRollback{at,from,to,auto,reason}`、`rollbacksInChain`、`autoRollbacksTotal`。

用户手动在设置里选版本的行为**未改动**（`backend:rollback-to` 那条 IPC 没碰）。

## 5. H-08（P1）AppUserModelID + 通知取证

### 5.1 AUMID（含 0.3.48 A 版缺陷复修：切片后失效 → 随包常量 + 门禁）

**首版（A 版）做法与它为什么错**：身份取自 `require('./package.json')` 的构建字段
（`build.appId`）。开发态正确，但 electron-builder 打包时会**重写 app 的 package.json
并剥离 `build` 段**（实测成品 asar 内 `package.json` 仅 503 字节、无 `build`）→
`setAppUserModelId` 在 shipped 包里**从未执行**，AUMID 保护整体空转。这类缺陷在
开发机与 CI 上永远复现不出来，是出包团队用 asar 实物核对才发现的。

**现做法（B 版）**：

```js
// app-identity.js（仓库根，*.js 已被 build.files 的 *.js 通配覆盖，不改构建清单）
const DSH_APP_ID = 'com.deepseek.dshdesktop';
assertAppId(DSH_APP_ID);                     // 加载即自检：非法直接 throw（不返回 undefined）
module.exports = { DSH_APP_ID, APP_ID: DSH_APP_ID, appId: DSH_APP_ID, … };

// main.js（模块加载期，早于 whenReady）
const { DSH_APP_ID } = require('./app-identity');
app.setAppUserModelId(DSH_APP_ID);
diag('AppUserModelID 已设置 aumidApplied:true appId=' + DSH_APP_ID + ' 来源=app-identity.js');
```

三条保障（缺一不可）：

1. **随包**：常量在普通 `.js` 里，被打进 asar，运行期不再读任何会被剥离的字段。
2. **单一事实源 + 防漂移**：构建侧权威值仍是 `package.json` 的 `appId`（安装器按它写
   快捷方式身份）；`scripts/app-identity-gate.js` 机械校验「常量 === build.appId」且
   「`main.js` 真的把它喂给 `setAppUserModelId`」，任一不满足即 `exit 1`，已串在
   `npm run dist` 前置链上。**两处写死的漂移变成构建失败，而不是靠记忆。**
3. **成品形态回归**：`scripts/test-h08-aumid.js §②` 把 `package.json` 换成**成品 asar
   内的形态**（无 `build` 段）再跑 main.js，断言 AUMID 仍生效、且 `require` 记录里
   没有 `./package.json` —— 直接锁死本次缺陷类型。

> 命名取舍：出包团队门禁的识别正则要求常量名形如 `…APP…ID…` **且 `APP` 前有字符**
> （`const APP_ID = …` 反而漏识别，见《…审计.md》§7.1）。本轮取 `DSH_APP_ID`
> 这一在"修正前/修正后"两种正则下都能命中的名字，并用别名暴露 `APP_ID` / `appId`，
> **字面量只有一处**。

### 5.2 通知通道：从"发出去就算完"到"可取证"

三个 `tray.displayBalloon(...)` 调用点收敛到唯一出口 `notifyUser(title, content, opts)`：

1. 每次发送都写诊断日志，带 `aumid` / `platform` / `silentDropRisk`；
2. 监听 Electron 的 `balloon-show`（气泡真的显示时才触发），1.5s 内等到 → 记"系统确认显示"；
3. 等不到 → 如实记"未收到 balloon-show 确认（疑似被系统丢弃）"，并改用 `Notification`（Windows Toast）**补发一次**；`Notification.isSupported()` 为 false 时明说"仅落日志"，不假装发过；
4. `displayBalloon` 抛错 → 立刻记"通道不可用"并补发；
5. 托盘不存在 → 直接走替代通道并记录"没有托盘"。

纪律对齐：**没有引入第二种确认流程**（`Notification` 与气泡同语义、无按钮、无回调），**托盘入口完整保留**。

### 5.3 与"禁止降级兜底"的关系

替代通道**只在观测到失败时**启用（`balloon-show` 未触达 / API 抛错 / 无托盘），且每次切换都留日志 —— 这是"把不可观测变成可观测"，不是"出错了悄悄换个通道继续"。真实的系统级气泡可见性仍需真机确认，见《…审计.md》§5 待确认项。
