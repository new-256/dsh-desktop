# H-10 修复方案：诊断日志从「逐行同步 IO」到「队列 + 批量刷盘」

> 版本 0.3.48 · 任务 task-7 · 写入域：`diag-log.js`（唯一所有者）
> 隐患出处：`分析_官方桌面端对比_2026-11-04/02_本地盘点/隐患清单.md` H-10（P1）
> 验收：`scripts/test-h10-log-throughput.js`（20 项断言，含 5 万行压力）

## 1. 问题本质

后端 stdout/stderr 每来一行 → `pushLog()` → `diag('后端输出', text)` →
`diag-log.write()` **在 Electron 主进程同步**执行：

```
rotateIfNeeded()  → fs.statSync            （每行 1 次）
fs.appendFileSync 主日志                    （每行 1 次）
ERROR_LINE_RE.test
命中错误 → fs.statSync + fs.appendFileSync 错误清单
         → fs.statSync + fs.appendFileSync 桌面报告   （每行最多 +4 次）
```

即「每行 2~5 次同步文件系统调用」，且全部在主线程。长会话/高频输出（插件批量构建、
错误风暴）时事件循环被同步 IO 堵住 → 窗口卡顿；磁盘写放大 2×。

## 2. 方案：内存队列 + 定时分块刷盘 + 显式背压

```
write(...)
  ├─ 格式化 + ERROR_LINE_RE 判定        （纯 CPU，无 IO）
  ├─ queuePush(record)                  （行数/字节双上限，触顶计数）
  └─ scheduleFlush()                    （200ms 定时器，unref）

定时器触发 flushPending()
  ├─ while (队列非空 && 未超 12ms 预算)
  │    takeBatch(≤256KB, ≤2000 行)      ← 一次 append 的粒度
  │    writeBatch():
  │       appendChunk(主日志, chunk, 10MB)   ← 追加前一次滚动检查
  │       疑似故障行 → appendChunk(错误清单, 2MB) + 桌面报告（固定名/2MB 上限）
  └─ 丢弃计数 > 0 → 写进日志正文 + stderr
```

### 2.1 为什么是「同步 + 定时」而不是「异步 append 链」

任务书允许两条路，选前者是为了**不丢行**这个硬语义：

- 异步链（`fs.promises.appendFile`）在 `process.exit` 瞬间可能把「已出队但未完成」的批次
  连人带包丢掉；要在退出时补写，就得面对"这批到底落没落盘"的不确定性 → 重写会重复、
  不写会丢行；
- 同步批量刷盘把「出队 → 写盘」压在同一个 tick 内完成，**不存在在途批次**，因此
  `exit` 钩子里只需把队列里剩下的行写完即可，语义干净。

代价是每 200ms 一次同步写（256KB 块 ~ 1ms 级），相对原来每行一次的阻塞是量级改善
（实测：入队 1.75~2.91µs/行，老路径形态 205~305µs/行；5 万行落盘共 78 次系统调用、22~25ms）。

### 2.2 语义保持（对照原行为逐条）

| 行为 | 0.3.47 | 0.3.48 | 保持 |
|---|---|---|---|
| 会话头 | 首次写入时写 `===== 会话开始 …` | 首次写入时入队同一行（同一批次内先于首行） | ✔ |
| 10MB 滚动 | 每次写入前 `statSync`，超阈值按时间戳切分存档，同秒加序号 | 每块追加前做同样检查，阈值常量与命名/序号规则不变 | ✔（粒度由「每行」变「每块 ≤256KB」，因此单文件最多超出阈值一个块） |
| 错误清单 2MB 滚动 | 命中错误行时先滚动再追加 | 每块命中错误行的批次先滚动再追加 | ✔ |
| 桌面报告 | 首次错误用覆盖语义写头 + `statSync` 判 2MB 上限后追加 | 同上，改在刷盘时执行（≤200ms 延迟） | ✔ |
| 存档清理 | 会话首次 + 每日 `housekeep()` | 不变（仍同步，但只在会话首次/每日触发） | ✔ |
| 桌面历史报告归档 | 会话首次 | 不变 | ✔ |
| 控制台回显 | `[diag] …` 每行都打 | 不变 | ✔ |
| 失败不影响主流程 | 全部 `catch` 后忽略 | `catch` 后 **`stderr` + 状态计数**，不静默 | ✔（更强） |

### 2.3 背压与「禁止静默丢弃」

- 上限：`QUEUE_MAX_LINES`（默认 100,000 行）/ `QUEUE_MAX_BYTES`（默认 32MB）；
- 触顶策略：**丢弃新到达的行**（已入队的行一定落盘），计入 `droppedLines`/`droppedTotal`；
- 下一次刷盘把计数**写进日志正文**，同时打 `stderr`：

```
[2026-11-03T17:12:49.096Z] ⚠ 诊断日志队列触顶（上限 100 行 / 33554432 字节）：本次丢弃 901 行，
累计丢弃 901 行；被丢弃的行仍完整打印在 [dsh-backend] 标准输出，可用控制台日志补齐
```

- `status()` 暴露 `droppedPending` / `droppedTotal` / `writeErrors` / `lastError` /
  `queuedLines` / `queuedBytes` / `flushCount` / `lastFlushMs`（不把计数藏在闭包里）。

### 2.4 退出 flush（四路口，缺一不可）

**先说结论：只挂 `process.once('exit')` 是不够的，实测会丢光队列。** 在真实 Electron 主进程里
写 3 行后直接 `app.exit(0)`，首轮磁盘上是 **0 行**：

| 退出方式 | `process 'exit'` | `before-quit`/`will-quit` | 结论 |
|---|---|---|---|
| 纯 Node `process.exit(0)` | 触发 | 不适用 | 单钩子够用（H-10 测试阶段 4 已验证 501 行全落） |
| Electron `app.quit()` | 触发（最终 exit） | 触发 | 够用，但依赖 Chromium 收尾时序 |
| Electron `app.exit(0)` | **不触发** | **不触发**（官方文档明确） | 单钩子 = 全丢；`main.js` 的「更新后重启」正是 `app.relaunch + app.exit(0)` |

因此 `diag-log.js` 装四路钩子，把"进程要没了"变成确定的 flush：

```js
process.on('exit', runAll)                       // ① 纯 Node / 正常收尾
electronApp.exit = (code) => { runAll(); raw(code) }   // ② app.exit（立即退出，唯一可靠口）
electronApp.on('will-quit', runAll)              // ③ 正常 app.quit 路径
process.exit = (code) => { runAll(); raw(code) }       // ④ 其他模块直接调 process.exit
```

- 多实例幂等：钩子集合挂在 `Symbol.for('dsh.diag.flushHooks')` 上，只安装一次包装器，各实例
  把自己的 `flushSync` 注册进去（测试里每阶段一套干净模块也不会重复包装）；
- 预算默认 **1000ms**（与 `crash-report.js` 的 1s 落盘上限对齐，不允许 flush 拖长退出）；
- 预算内没写完：剩余行数写进日志正文 + `stderr`，并计入 `droppedTotal`（**不静默**）；
- 对外导出 `flushSync(budgetMs)`：`main.js` 若想在退出流程里提前落盘可直接调用
  （属 main.js 写入域，本任务未改）。

### 2.5 关键产物 vs 高频行：durability 分层（0.3.48 回归后补）

**回归现场**（lead 复现，见审计文档 §2.7）：`scripts/test-047-desktop-report.js` 15 项里 4 项红
——「本次启动后：桌面只剩一份报告」「桌面报告改为固定名」「上一轮的固定名报告已归档」
「第二次启动出错后：桌面又只有一份」。根因不是测试过时，而是第一版 H-10 把**所有**写入都
套进了 200ms 批量：`write('模拟错误…')` 返回时「桌面错误报告」还没被创建，而 0.3.47 的桌面
报告纪律与 `crash-report.js` 的契约都要求「出错后这份报告 1s 内就要能被对话框/用户按文件名
读到」。**高频行可以晚 200ms，关键产物不行。**

**分层（判据是机制，不是文件名清单）**

| 层 | 谁属于这层 | 判据 | 落盘时机 |
|---|---|---|---|
| 批量层 | 后端 stdout/stderr、普通 `diag()` 行 | 记录**只**进主日志（10MB 滚动文件），没有任何「返回后立刻被读」的契约 | 200ms 定时分块刷盘（H-10 的收益全在这层） |
| durability 层 | 错误清单、桌面错误报告，以及调用点显式声明的产物（迁移记录、隔离记录、更新决策…） | ① **去向判定**：命中 `ERROR_LINE_RE` 的记录必然写进错误清单 + 桌面错误报告 → 自动 durable；② **显式声明**：`writeDurable(...)` | `write()` / `writeDurable()` **返回前**已在磁盘上 |

判定函数只有一行、且只看「去向」：

```js
function feedsCriticalSink(record) { return record.isError === true; }
...
const durable = forceDurable || feedsCriticalSink(record);
```

**为什么不是「写死文件名」**：代码里没有任何产物文件名参与分类。将来新增一个关键产物
（例如「插件隔离决定记录」），只需调用点写 `writeDurable(...)` —— 而不是往判定函数里加
`if (文件名 === '...')`。反向也成立：一条含 "error" 字样的后端输出哪怕进的是迁移日志，
它既然会进错误清单/桌面报告这两个关键产物，就必须 durable —— 因为**读者的契约**决定了
时机，不是它叫什么。

**durable 的实现语义（屏障 + 直写）**

```js
flushSync(FLUSH_BUDGET_MS);   // ① 屏障：先把更早的高频行同步刷干净（保证顺序）
writeBatch([record]);         // ② 直写：不进队列 → 不受队列上限/丢弃计数影响
```

- **顺序**：关键记录不会插队到更早的行前面（测试 D1~D3 断言 202 行顺序完整）；
- **队列上限**：关键记录不进队列，因此永远不会因背压被丢弃（背压只影响高频行）；
- **预算**：复用退出刷盘的 1s 上限；超预算会按既有纪律把未落盘行数写进正文 + stderr，
  不静默（正常场景队列只有 200ms 的量，实测单次 durable 在毫秒级）；
- **崩溃路径**：`crash-report.js` 自己用 `writeFileSync` 落报告、独立于本模块，1s 预算不受影响。

**将来新增产物时怎么判**：一句话 ——「写入返回后 1s 内，会不会有别的代码或人**按文件名**
去读这个文件？」会 → durability 层（`writeDurable`）；只是给人翻的流水 → 批量层。

## 3. 已知取舍（必须写清，避免被当成"无损异步"）

1. **硬杀窗口**：进程被任务管理器强杀 / BSOD 时任何钩子都不会执行，最多丢失最近
   **≤200ms** 的队列行。缓解：这些行同时通过 `[dsh-backend]` / `[diag]` 打到标准输出
   （`main.js` 的日志转发仍在），控制台侧可补齐。正常退出路径（`app.quit`、`app.exit`、
   `process.exit`、纯 Node 退出）都已验证不丢行。这是同步写换成批量写的固有代价，
   已用 200ms 周期把它压到最小。
2. **故障重试可能重复**：磁盘写入失败时整批回队重试（保「不丢」），若失败发生在
   「主日志已写、错误清单未写」的中间态，重试会让该批主日志行重复一次。取舍是
   **宁可重复，不可丢行**，且每次失败都进 `stderr` 与 `writeErrors`。
3. **桌面报告降级可见**：桌面报告是"给用户看的副本"，它写失败不重试（重试会重复错误
   清单行），但会 `stderr` + `writeErrors` 记账，不假装成功。
4. **滚动粒度**：单文件可能超出阈值一个块（≤256KB），比原来"每行精确卡 10MB"略宽松；
   10MB 阈值与命名/保留策略不变。
5. **错误行的同步代价仍然存在（有意为之）**：命中 `ERROR_LINE_RE` 的行是 durable 的，
   错误风暴下这些行仍是「逐行同步写 2 个产物」——与 0.3.47 完全一致，**不是新引入的**
   退化；H-10 省下的是占绝大多数的普通输出行。若将来错误风暴本身成为瓶颈，正确的方向是
   「错误清单改用有界聚合 + 1s 内可视」而不是把关键产物改回批量（那会重现本次回归）；
6. **durable 的强语义边界**：durable 只保证「本进程写出的字节已交给文件系统」（`appendFileSync`
   返回），不等于 `fsync` 落盘到物理介质。断电场景仍可能丢最后一段 —— 与 0.3.47 的
   `appendFileSync` 语义相同，本任务不改变这条边界。

## 5. 后续建议（属他人写入域，本任务未做）

1. `main.js` 的 `pushLog()` 目前把后端原始输出**全量**转发进诊断日志（写放大 2×）。建议按
   隐患清单建议降级为 `debug` 级（默认不落盘），可再砍一半磁盘写入 —— 需改 `main.js`；
2. `main.js` 退出流程（`restartApp` / `quitGuard.now`）里可在 `app.exit()` 前显式调用
   `diagLog.flushSync()`，把"最后一句日志是否落盘"从依赖 `exit` 钩子变成确定性动作；
3. 若将来需要"绝不丢任何一行"，可把队列落盘改成 `fs.createWriteStream` + 崩溃前 `fsync`
   的文件句柄方案 —— 但要同时解决 Windows 下「重命名被占用文件」的滚动冲突（需关闭句柄后
   再改名），复杂度显著上升，当前 200ms 批量已满足卡顿治理目标。
