## 1. 结构决策：为什么新增两个模块而不是就地改 main.js

`PROJECT_RULES.md §3`：`main.js` 不得继续就地膨胀，新增逻辑落新文件、main.js 只做接线。因此：

```
url-policy.js（纯函数，零 electron 依赖）
  decideNavigation({target, currentOrigin, allowedFileRoots}) → {allow, kind, reason}
  decideWindowOpen({target, currentOrigin, externalHostAllowlist}) → {action, reason, url}
  originOf / sameOrigin / isLoopbackHost / normalizeHost / resolveExternalHostAllowlist / describeDecision

session-hygiene.js（纯计划 + 薄执行）
  planCleanup(cookies, policy) → {remove[], keep[{reason}], byHost}
  createCookieHygiene({session, log}).clean(policy) → {scanned, removed, failed, stillThere, byHost, kept}
  resolveNamePrefixes / shouldPurgeAllLoopback / cookieRemovalUrl / summarizeResult
```

`main.js` 只提供"当前窗口属于谁"的上下文、执行副作用（`preventDefault`、`shell.openExternal`、`cookies.remove`）与日志。

## 2. B-05 安全边界三件套

### 2.1 sandbox:true（主窗 + 设置窗 + splash）

- 主窗 `main.js:1706`、设置窗 `main.js:2523`、splash `main.js:1285` 全部 `sandbox: true`，并显式 `webSecurity: true`（主/设置窗）。
- **preload 依赖核实**（开 sandbox 前必须做）：
  - `preload.js` 只 `require('electron')` 的 `contextBridge`/`ipcRenderer` + 读 `process.platform`（sandbox 下 `process` 是受限 polyfill，`platform` 仍可用）；
  - `settings-preload.js` 同样只用 `electron` 两个 API + `process` 无依赖；
  - 两者都**没有**用任何 Node 内建（`fs`/`path`/`child_process`…）。→ 不需要 `nodeIntegration`，也没有"为了开 sandbox 而偷加 nodeIntegration"。
- **自证**：`logEffectiveWebPreferences()`（`main.js:1518`）用 `webContents.getLastWebPreferences()` 读回 **Electron 实际生效**的配置并落日志（不是我们写进去的字面量）：
  `{"window":"main","sandbox":true,"contextIsolation":true,"nodeIntegration":false,"webSecurity":true}`。

### 2.2 导航白名单（will-navigate）

- **两个窗口**都装（0.3.48 只有主窗，且**根本没有**导航处理器）：`applyWindowHandlers(win, {kind, allowedFileRoots, ownUrl})`（`main.js:1477`）。
- 判定规则（`url-policy.decideNavigation`）：
  1. 解析失败/空 → 拒（`unparsable-url`）；
  2. `about:blank` → 拒；
  3. 协议不在 `http/https/file` → 拒（`protocol-not-allowed`）；
  4. `file:` → 只允许应用自身目录内（`app-file`），目录外拒（`file-outside-app`）；
  5. `http(s)` → **只允许与当前窗口 origin 完全一致（含端口）**，其余拒（`cross-origin-navigation`）。
- 关键取舍：**不能用"是否回环"判定**。页面若被允许跳到另一个 `127.0.0.1:<其它端口>` 的本地服务，它依然挂着我们的 preload 与 IPC 授权 —— 那等于把应用窗口交给别人的页面。所以按 origin（含端口）精确匹配；端口每次启动都变，所以用"当前 origin"动态给上下文，不写死。
- 主窗 origin 来源：`activeUrl` → 兜底建窗时传入的 `ownUrl`（建窗发生在 `activeUrl` 赋值前后都可能，不能让判定因此退化成全拒）。

### 2.3 开窗默认拒 + 外链白名单（B-11）

`setWindowOpenHandler` 恒返回 `{action:'deny'}`；唯一"放行"是交给系统（`shell.openExternal`）。规则（`decideWindowOpen`）：

| 输入 | 结果 | 理由 |
|---|---|---|
| 与当前窗口同源 | deny | 我们不需要任何子窗口（多一个窗口=多一份 preload+IPC 面） |
| 协议 ∉ {http, https, mailto} | deny | `file:`/`javascript:`/`data:`/自定义协议会让系统执行东西（B-11 核心） |
| URL 含 username/password | deny | `https://user:pass@host/` 是经典钓鱼形态 |
| 主机含非 ASCII（看**原始字符串**） | deny | WHATWG URL 会把 Unicode 主机洗成 punycode，只看解析结果会漏掉同形字 |
| http(s) 且主机是回环 | deny | 我们自己的 UI/本地服务不该丢进系统浏览器 |
| 配了 `DSH_EXTERNAL_HOST_ALLOWLIST` 且主机不在清单 | deny | 可选收紧（配置驱动，不写死域名） |
| 其余 http(s) / mailto | **open-external** | 交给用户自己的浏览器/邮件客户端 |

> 为什么 `http:` 也在白名单：它打开的是用户自己的浏览器；真正危险的是"让系统执行本地东西"的协议。需要更严时用 `DSH_EXTERNAL_HOST_ALLOWLIST=github.com,deepseek.com` 收紧（支持子域）。

## 3. B-01 旧后端 cookie 清理

### 3.1 机理与边界

- 后端 `--port 0` 每次换端口，而 **cookie 作用域忽略端口**（RFC 6265）→ 旧端口的 cookie 会跟随新端口的请求，表现为"莫名重登 / 接口莫名报错"。
- 清理**必须在绑定新端口之前**（`main.js` step 5 之前调 `cleanLegacyBackendCookies()`，见 §6.1），否则旧 cookie 已随首个请求发出。
- **清理边界（唯一真实风险）**：`127.0.0.1` 是公共命名空间，别的本地工具也在上面种 cookie。所以默认**双重限定**：
  ① 主机 ∈ {127.0.0.1, localhost, ::1}；② cookie 名命中本产品前缀（默认 `dsh`/`dsh-auth`/`dsh-session`/`dsh-desktop`，可用 `DSH_COOKIE_NAME_PREFIXES` 覆盖）。
  两条同时满足才删；不满足的一律"保留 + 记录原因"（`not-our-host` / `name-prefix-mismatch`），便于事后核对"为什么它没被清"。
- 显式开关 `DSH_COOKIE_PURGE_ALL_LOOPBACK=1` 才清空回环全部 cookie（默认关，避免误伤）。
- 清理后**复核**：`cookies.get({})` 再读一次，remove 报成功但实际还在的进 `stillThere`（不虚报成功）。
- 失败不静默：诊断日志 + 后端日志各一条（扫描/清除/保留/失败/仍存在），且**不阻断启动**（cookie 清理失败不该让用户打不开应用）。

## 4. 阶段一遗留接线（3 项）

1. **profile 隔离结果用户可见化**（`recordIsolationOutcome()`，`main.js:1125` 调用）：
   `abandoned=true` → 一次性提示"本轮隔离已放弃/你的插件目录保持原样"+ 原因 + 副本位置；
   发生过 `restore` → 提示"删原目录未完成，已用校验过的副本还原（补回 N 文件/M 链接）"或"还原未完全成功（完整副本仍在）"。
   提示走**延后队列**（启动早期入队，主窗口就绪后一次性非阻塞弹出）—— 避免早期模态框把启动链卡住。
2. **H-05 中断态入动作表**：启动早期 `mgr.interruptedApplyState()`（step 3.1）记录磁盘事实（dsh / dsh.old / dsh.previous / dsh.new 各自版本 + 建议恢复动作 + 是否 marker 不可解析），并：
   - 故障弹窗标题变为「上次更新未完成，后端没能启动」；
   - detail 附 `interruptedApplyBrief()`（磁盘事实 + 恢复动作）；
   - 中断态作为**直接证据**参与回滚决策（`recommendRollback=true`）；
   - **回滚目标按磁盘事实解析**（`resolveRollbackTarget()`）：`dsh.previous` 可用 → 走 `mgr.rollbackDsh()`；仅 `dsh.old` 可用**且当前 dsh 缺失** → `promoteDshOldToLive()`（保留归档目录 `dsh.broken-<ts>`，不删除）；两者都没有 → 不提供按钮。按钮文案直接写明用哪份旧版本。
   - `dsh.old` 分支为什么在主进程实现：`updater-backend.js` 不在本任务写入域，且它未导出 dsh.old 恢复原语。已在审计里登记为"跨团队所有权债"，建议后续移入 updater-backend。
3. **IPC 按窗口身份分权**（`main.js:216-235`）：
   - `SETTINGS_WINDOW_CHANNELS`（22 条，与 `settings-preload.js` ALLOWED_CHANNELS **逐项一致**）只对设置窗开放；
   - `MAIN_WINDOW_CHANNELS`（`app:get-version`/`app:device-info`/`app:restart`/`backend:check-updates`/`backend:versions`/`env:isolation`）只对主窗开放；
   - 越权尝试 → 抛错 + `diag('已拒绝越权 IPC：…')`（可归因到注入链）；
   - 两条不变量由测试守住：**所有已注册通道都被某个窗口认领**（否则运行期被拒=静默功能丢失）、**两份清单无交集**。

- 删除旧的两行定时器（`main.js` HEAD 版 **L1963-1964**：`setTimeout(... 5000)` + `setInterval(... 6h)`），改为 `startBackendUpdateLoop()`（现 `main.js:3017` 调用，`main.js:3036` 定义）。

### 5.4 H-01 对 copy 兜底路径的确认

`applied/copy` 路径产出的 `dsh.previous` 会被 `resolveRollbackTarget()` 的首选分支命中（判据：`dsh.previous/node_modules/@deepseek-ai/dsh/lib/bin.js` 存在）→ 故障弹窗照常出现「回滚到上一个版本（<版本>）」。因此 H-01 的自动/手动回滚在 copy 兜底路径上**同样可用**；updater 报告的 `applied=0.4.1 / dsh.previous=0.4.0` 实测与该判据一致。
