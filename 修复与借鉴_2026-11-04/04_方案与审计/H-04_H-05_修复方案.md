## 一、H-04（P0 · 数据丢失）profile 隔离兜底不得删用户数据

### 1. 问题（隐患清单 H-04 原文证据）

修复前 `quarantineProfiles()`（原 `:1707-1720`）：`rename(profiles → profiles.broken-<ts>)` 失败后
直接 `rimraf(prof)` —— 把用户整棵 `profiles` 树**物理删除**。而 README 承诺「启动自愈最坏也
只是把 profiles 隔离备份成 `profiles.broken-时间戳`（保留最近 2 份），**不删任何数据**」。

### 2. 根因（三层，逐层都能独立造成数据丢失）

| 层 | 根因 | 后果 |
|---|---|---|
| 代码结构 | 兜底分支把「隔离」实现成「删除」，`rimraf` 是唯一补偿动作 | 删完即不可逆 |
| Windows 语义 | `rename` 失败的真实原因（句柄未释放 / 杀软扫描 / 索引服务）**同样**会阻断后续 unlink | 兜底分支在真实触发条件下必然会走，不是理论风险 |
| 承诺一致性 | 唯一补偿 `profiles-registry-<ts>.json` 只存 `bundles` / `dependencies` 名称与 patch 文本 | 依赖实体（`node_modules` 里的真实文件）永久丢失，表现为「插件都在但都装不上」 |

附带发现（审计新发现，见审计文档 R-1）：`pruneQuarantineProfiles()` 用前缀正则
`/^profiles\.broken-/i` 判归属，用户手工建的同前缀目录（备份意图）也会被当自家产物清掉。

### 3. 方案（改后的失败顺序）

```
quarantineProfiles(home)
 ├─ rename(profiles → profiles.broken-<ts>)  ── 成功 ──► quarantined=true（不删任何东西）
 └─ 失败（EPERM/EBUSY 等）
     ├─ 复制到 profiles.broken-<ts>
     │   · copyTreePreservingLinks：**绝不进入 link 目标**，junction/symlink 只在目标侧重建链接
     │   · 读不到（EPERM/EBUSY）立即抛错 → 半份副本不算成功
     ├─ 校验 measureTree（files / dirs / links / bytes 四项全等）
     │   · 校验不过 → 删掉我们刚建的半成品副本 → **放弃本轮隔离**
     └─ 校验通过（此刻用户数据已有完整副本）
         ├─ removeOwnedDirectory(profiles)   ← 只有到这里才允许删原树
         │   ├─ 删除完成 → quarantined=true（副本保留，prune 维持最近 2 份）
         │   └─ 删除被同一占用挡到一半
         │       └─ restoreLiveTreeFromCopy：用**已校验副本**只补缺失项（被占用文件本就没删）
         │           → 原树恢复到删除前逐项一致 → abandoned=true + reason + restore 结果
         └─ 全程写诊断日志（含校验口径、还原数量），结论经返回值上报
```

返回契约（`main.js` 现有调用点 `const qRes = …quarantineProfiles(p.dshHome) : null` 不变）：

```js
{ quarantined,              // 原目录是否**整体**离开原位（rename 成功，或复制校验后删除成功）
  name, path,               // 隔离目录（copied=true 时即使是"放弃"也指副本，便于取证）
  fallback,                 // 是否走了复制兜底
  copied,                   // 复制+校验是否成功
  abandoned,                // 本轮隔离是否被放弃（复制失败 / 删除失败后已还原）
  reason,                   // 放弃原因（人可读，不吞错）
  removal, restore,         // 删除结果 / 还原结果（逐项证据）
  registryFile, registry }  // 与既有行为一致
```

关键落地位置（0.3.48）：

| 符号 | 行 | 作用 |
|---|---|---|
| `QUARANTINE_NAME_RE` | `:1611` | 清理只认本程序命名的隔离目录 |
| `measureTree` | `:1618` | 复制校验口径（读不到就抛错） |
| `copyTreePreservingLinks` | `:1642` | 不跟随链接的复制 |
| `quarantineProfilesByCopy` | `:1674` | 复制 → 校验 → 失败清理半成品 |
| `restoreLiveTreeFromCopy` | `:1704` | 删除未完成时用副本还原原树 |
| `pruneQuarantineProfiles` | `:1741` | 保留 2 份 + 严格命名匹配 |
| `quarantineProfiles` | `:1830` | 编排 + 全量证据上报 |

### 4. 影响面

- 只影响 `rename(profiles)` **失败的兜底分支**（自愈阶梯 R2 级，由 `ladder-policy.attemptStage` 裁决）。
  正常路径（rename 成功）行为完全不变，只是多了返回值字段。
- `main.js` 的两条文案分支（`qRes.fallback ? "清理完成" : "已备份为 …（未删除）"`）**不需要改**：
  `quarantined=true ∧ fallback=true` 的语义是「原树已删、完整副本在 `qRes.name`」，与「清理完成」一致。
- `pruneQuarantineProfiles` 收紧命名匹配后，历史遗留的非规范名目录不再被自动清理（只增不减，安全侧）。
- 新增耗时只发生在兜底路径：一次完整复制 + 两次 `measureTree` 遍历（复核见审计 R-6）。

### 5. 回滚方式

单一文件、单函数族，可整块回退：

- `git checkout -- updater-backend.js` 会同时回退 H-05（不建议单独用）。
- 精确回滚 H-04：把 `quarantineProfiles` 的 `catch` 分支恢复为 `rimraf(prof)`，并删除
  `QUARANTINE_NAME_RE` / `measureTree` / `copyTreePreservingLinks` / `quarantineProfilesByCopy` /
  `restoreLiveTreeFromCopy` 五个符号；`pruneQuarantineProfiles` 的 `QUARANTINE_NAME_RE.test(entry)`
  改回 `^profiles\.broken-` 前缀判断。回退后必须同时把 `scripts/test-043.js` 的 3 条断言翻回去。
- 回退触发条件：若线上出现「隔离后启动仍失败，且日志显示 `restore` 反复失败」——先把
  `apply-in-progress.json` 与 `profiles.broken-*` 保留取证，再回退（副本可人工还原）。

## 二、H-05（P0 · 静默回退）`applyStaged` 缺「进行中」标记

### 1. 问题（隐患清单 H-05 原文证据）

`applyStaged()`（原 `:3880-3917`）交换目录时存在两个不可逆窗口：
① `dsh` 已改名为 `dsh.old`、`dsh.new` 还没顶上来（`dsh` 不存在）；② `dsh.new` 已消费、旧树还没落到
`dsh.previous`。窗口内进程死亡（断电 / 强杀 / BSOD）后，下次启动 `ensureSeeded()` 依据
`needDsh = !existsSync(dshBin)` 直接从 payload 解压**出厂版本**，用户刚更新的后端被静默降级，
日志里只留一行 seeding；且 `dsh.old` 残留、`versions.json` 被覆盖。

### 2. 根因

- 交换动作**没有前置意图记录**：journal 只在**成功之后**才写 `applied`，交换期间磁盘上没有任何
  「我正在换」的证据，于是「交换中有没有发生过」在事后不可判定。
- `ensureSeeded()` 的判据只问「dsh 在不在」，不区分「还没装过」与「换到一半被砍」，因此把
  「可恢复的中间态」误判成「需要出厂 seed」——这是同一条缺失标记导致的两个后果。

### 3. 方案

标记文件：`%APPDATA%\DSH Desktop\backend\apply-in-progress.json`（与 `update-journal.json` **同域同目录**）

```json
{ "schemaVersion": 1, "operationId": "<ts36-rand>", "startedAt": "<ISO>", "pid": 1234,
  "step": "dsh-swap" | "dsh-hidden" | "dsh-swap-failed" | "dsh-swap-unverified",
  "from": "<旧版本>", "to": "<目标版本>", "updatedAt": "<ISO>", "detail": "…", "onDisk": "…" }
```

生命周期（`applyStagedDshSwap`）：

```
1) beginApplyInProgress({step:'dsh-swap', from, to})     ← 交换之前
     └─ 写失败 → **不交换**：dsh/dsh.new 原样保留，journal 记 ERR_UPDATER_APPLY_MARKER_FAILED
2) swapDshDirectories（4 次 rename 重试）
     └─ 每次进入窗口 A 后立刻 updateApplyInProgress(step:'dsh-hidden')  ← 断电现场可精确判定
3) 交换未达成 → 保留标记 + journal ERR_UPDATER_APPLY_INCOMPLETE
4) 交换达成 → verifyAppliedDsh(staged)：bin.js 存在 + package.json 版本与暂存版本一致
     ├─ 校验不过 → **保留标记**（step:'dsh-swap-unverified'）+ journal ERR_UPDATER_APPLY_UNVERIFIED
     └─ 校验通过 → journal applied → clearApplyInProgress(operationId)（只清自己那一次）
```

启动早期读取端（`detectInterruptedApply`，由 `ensureSeeded()` 在**任何 seed 决定之前**调用，
因此不需要改 `main.js` 就已接电）：

```
active:false                                   ← 没有标记，一切照旧
active:true, step/target/startedAt,            ← 非静默：诊断日志 + 一条 journal
  live / old / previous / staged（各树版本）       （同一标记只记一条，不刷屏）
  recovery: 'swap-maybe-not-applied' | 'apply-maybe-completed'
          | 'restore-from-dsh.old' | 'restore-from-dsh.previous' | 'reinstall-required'
  unreadable: true（标记被写坏时仍按中断处理，不当没看见）
```

- **不自动恢复**：恢复动作（`dsh.old` / `dsh.previous` 换回）只暴露状态，决策权在启动链 /
  `showFatal`（H-01 范围）。不弹窗（弹窗是 `main.js` 职责）。
- 清除入口：`clearApplyInProgress()`（不给 operationId 时无条件清除），供主进程「已向用户交代过」后确认。
- 台账纪律：**不新增第二套台账**——`update-journal.json` 仍是唯一 append 台账（新增 3 个分类码
  `ERR_UPDATER_APPLY_INCOMPLETE/UNVERIFIED/MARKER_FAILED` + `ERR_UPDATER_APPLY_INTERRUPTED`；
  `journalUnverified()` 语义未变，仍只看 `state==='applied'`）。`apply-in-progress.json` 是一次操作的
  生命周期信封（覆盖写、天然不增长），不是历史流水。

关键落地位置（0.3.48）：

| 符号 | 行 | 作用 |
|---|---|---|
| `APPLY_IN_PROGRESS_FILE` / `applyInProgressPath` | `:3772` | 标记位置（与 journal 同域） |
| `readApplyInProgress` / `beginApplyInProgress` / `updateApplyInProgress` / `clearApplyInProgress` | `:3776-3823` | 标记生命周期（写失败即抛，不降级） |
| `probeDshTree` | `:3826` | 单棵树版本探测 |
| `detectInterruptedApply` / `interruptedApplyState` | `:3843/:3891` | 启动早期检测 + 缓存暴露 |
| `verifyAppliedDsh` | `:4183` | 「交换成功」的唯一判据 |
| `swapDshDirectories` / `swapDshByCopy` / `applyStagedDshSwap` | `:4205/:4239/:4256` | 从 `applyStaged` 抽出的交换全过程（可读、可测、圈复杂度 ≤ 10） |
| `ensureSeeded` 首行 | `:1290` | 检测先于 seed（时序保证） |
| `journalAdd` | `:3707` | 显式错误码优先（否则被原文里的 EPERM 抢先匹配、归因错位） |

### 4. 影响面

- `applyStaged()` 对外签名/返回值不变（`{dsh, node}`）；`main.js` 步骤 3 的 `diag(...)` 与
  `applyStaged` 后逻辑无需改动。
- 新增一次小文件写 + 至多 2 次步骤更新（每次 <1ms），仅在**确有暂存更新**时发生。
- 失败语义变化（有意的）：`applyStaged` 在「标记写不进去」时**拒绝交换**——这是「禁止降级兜底」
  的直接体现：宁可不更新，也不制造不可判定的中断。
- `ensureSeeded()` 每次启动多 4 次 `existsSync` + 4 次小 JSON 读取（可忽略）。
- journal 多 4 个错误码；`journalMarkVerified()` 推进逻辑不受影响。

### 5. 回滚方式

- 整块回退：删除 `apply-in-progress` 标记族 6 个函数与 `verifyAppliedDsh` / `swapDsh*` /
  `applyStagedDshSwap`，把 `applyStaged()` 的 dsh 段恢复为原内联循环，并去掉 `ensureSeeded` 首行检测
  与 4 个 journal 错误码。
- 运行时止血（不回退代码）：直接删除 `backend\apply-in-progress.json` 即可让下次启动不再报中断
  （但会丢掉本次中断的证据，删前请先留存）。
