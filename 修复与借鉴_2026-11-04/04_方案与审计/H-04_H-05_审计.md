## 1. 残余风险

### R-1【需接线·中】`main.js` 对 `abandoned` 没有用户可见文案

`main.js:829-834` 只分支 `qRes.quarantined` / `qRes.fallback`。当本轮隔离被放弃
（`quarantined=false, abandoned=true`）时，**用户界面上什么都不会出现**，只有诊断日志里那句
`复制隔离失败，已放弃本轮隔离…`。返回值已带 `abandoned/reason/removal/restore`，接一句话的成本很低。
- 影响：用户在「隔离没成功」时拿不到任何提示，接着会看到自愈阶梯继续往下走（Node 重装 → showFatal）。
- 建议：`pushLog('本轮 profile 隔离已放弃（' + qRes.reason + '），原目录保持原样。\n')`。

### R-2【需接线·中】中断态没有用户可见出口（H-05）

`ensureSeeded()` 已调用 `detectInterruptedApply()`，所以**检测是真接电的**；但「告诉用户
『上次更新被打断，可回滚到 dsh.previous』」必须由 `main.js` 消费
`interruptedApplyState()`（已导出）+ 在 `showFatal`/托盘里加一句。当前状态：日志与 journal 有记录，
UI 无。
- 与之重叠的是 H-01（回滚接线，另一团队）。建议 H-01 接线时直接读 `interruptedApplyState().recovery`
  作为按钮启用依据（`restore-from-dsh.old` / `restore-from-dsh.previous` 时提示可回滚）。

### R-3【逻辑·中】`applyStaged` 的 copy 兜底仍然是「叠加覆盖」，且不产出 `dsh.previous`

`swapDshByCopy()`（历史行为，本次**未改**）：4 次 rename 全失败后，把 `dsh.new` 用 `copyDir`
（robocopy `/E`）覆盖进 `dsh`，随后 `rimraf(dsh.new)`。
- 问题 1：叠加而非替换 —— 新版本**删掉或改名**的文件会作为旧版残留留在 `dsh` 里，可能造成
  「新旧混合树」；`verifyAppliedDsh` 只校验 bin.js + 版本号，**看不出混合树**。
- 问题 2：该路径不产生 `dsh.previous`，等于这次更新没有回滚素材（H-01 需要它）。
- 为什么这次不改：它与 H-04 的复制兜底是两件不同的事（一个在 backend 树、一个在 dsh 树，后者由
  robocopy 提供原子性之外的便利），改动会扩大本次审计面。建议阶段二把 `swapDshByCopy` 换成
  「复制到 `dsh.new.tmp` → 校验 → 再 rename」，或在混合风险存在时直接放弃本轮应用。

### R-4【逻辑·低】`applied` 已写入但标记未清除之间的崩溃会误报一次中断

顺序是 `journalAdd(applied)` → `clearApplyInProgress()`。若在这两步之间死亡：下次启动既有
`applied` 记录又有标记 → 判为中断。此时 `live` 存在 → `recovery='apply-maybe-completed'`，
不会自动动作，只是多一条 journal + 一条日志。**属如实上报，可接受**，但如果后续 H-01 依据
`recovery` 自动回滚，需要把 `live.version === marker.to` 视为「已完成」而不是「中断」。

### R-5【性能·中】兜底复制是同步大盘 IO

`copyTreePreservingLinks` + 两次 `measureTree` 全在主进程同步执行。真实机器的
`profiles/*/node_modules` 可达数百 MB：复制可能让启动卡住数十秒（只在 rename 失败时发生，
但那时用户已经处在「启动失败」的糟糕时刻，再叠加几十秒无响应会很糟）。
- 建议阶段二：①先只复制「注册层」（`profiles/*/package.json`、`cordis.patch.yml`、manifest），
  依赖实体另行后台复制；②或把兜底搬到 `main.js` 的异步阶段并给 splash 文案。
- 现状缓解：`measureTree` 是纯 stat 遍历（不读内容），复制用 `fs.copyFileSync` 单文件调用。

### R-6【语义·低】`quarantined=false ∧ copied=true` 时 `name/path` 仍指向副本

这是**有意**的（副本要留给取证与人工还原），但会让只读 `name` 的下游误以为「隔离成功了」。
已用 `quarantined` / `abandoned` 两个布尔区分，且 `main.js` 只在 `quarantined` 分支使用 `name`。
【建议】后续消费方一律先看 `quarantined`。

### R-7【进度·低】中断标记长期不清会每次启动写一条诊断日志

`detectInterruptedApply()` 每次启动都会 `log()` 一行（这是「不静默」的要求），journal 侧已去重。
若 `main.js` 永不调用 `clearApplyInProgress()`，这行日志会一直出现。
- 判断：正确且必要（用户应当每次都能看到「上次更新被打断」），不算噪声。
- 退出条件：主进程确认处理后清除即可。

### R-8【测试·中】「断电」是模拟，不是真断电

H-05 的断电场景是**按代码路径手工构造磁盘现场**（标记 + `dsh` 缺失 + `dsh.old` 在位），
并在 `dsh.new → dsh` 的 rename 瞬间用 monkeypatch 抓取标记内容证明「标记先于交换」。
【未验证】真正的进程在 `Atomics.wait`/`rename` 中间被强杀后的文件系统状态（NTFS 日志回放结果）。
- 建议阶段二：真机断电演练（或 `procdump -t` 强杀 + 重启）一次，把 `apply-in-progress.json`
  与 `update-journal.json` 一并留档。

### R-9【测试·中】两个新脚本依赖 Windows 真实占用与 ACL

- 占用：pwsh 以 `FileShare.ReadWrite`（不共享 DELETE）持句柄 —— 实测能让 `rename` 返回 EPERM
  （曾在 4 种候选手段里逐一探测，见 `03_调试阶段` 输出）。若某机器上 `pwsh` 不存在，场景 2/3 会
  退化为「rename 竟然成功」并直接断言失败（不做静默跳过）——这是有意的：**测试基础设施缺失
  必须暴露**，不允许假装通过。
- ACL：用 `icacls /deny <user>:(RD)` 制造复制读取失败，`finally` 与 cleanup 两处撤销。
  若撤销失败，临时目录会残留并打印路径（不掩盖）。
- 【未验证】在非管理员账户、组策略禁用 `icacls` 的机器上的行为。

## 2. 调试期间发现的两个环境事实（对后续修缺陷有用，建议入知识库）

1. **`fs.cpSync` 在 EPERM 下会直接 fail-fast 杀掉进程**（实测 exit code `-1073740791` =
   `0xC0000409`，无 JS 异常、无 `exit` 钩子输出）。所以「复制失败」的兜底**绝不能**用 `fs.cpSync`，
   必须自己 walk + `copyFileSync` 才能拿到可 catch 的错误。这也是 H-04 兜底自己实现复制的原因之一。
2. **`icacls /deny <user>:(DE)` 并不能阻断目录 rename**（实测 rename 成功），但
   `/deny :(RD)` 能让 `readdir` 返回 EPERM，可用于构造「复制读取失败」；而
   **`FileShare.ReadWrite`（不共享 DELETE）的句柄确实能让 `rename` 返回 EPERM** —— 这是最接近
   杀软扫描的造错手段，已固化进脚手架 `holdFileHandle()` + `waitRenameBlocked()`（先探测真被占用
   再调用业务函数，不靠 sleep 猜）。
