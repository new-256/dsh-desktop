## 3. 踩到的坑与定位过程（真实记录）

### 坑 1：结构断言把"注释里的旧代码"当成了真代码

`test-h02 §①` 的断言 `!/new\s+Promise\s*\(\s*async\b/` **失败**了，实际值 1 处。
定位：修复注释里需要引用"旧结构长什么样"（`prepareBackendSpawn` 的块注释），因而注释里确实出现了 `new Promise(async (resolve, reject) => {…}` 字样。
处置：断言改为先剥离 `/* */` 与 `//` 注释再匹配（`codeOnly`）。这不是"放宽断言"，而是把断言对准**可执行代码**；另外补了一条"敏感度对照"用例（旧结构在同样输入下 800ms 不 settle）来保证测试非空转。

### 坑 2：读日志读不到刚写的行 —— 因为 `diag-log` 已经改成批量 flush

`test-h01 §②` 的"诊断日志写明回滚后的版本"**失败**，实际值是空数组（一行都没匹配到），但流水线上明明打印了 `回滚（auto）完成：1.0.0-test → 0.9.0-previous`。
定位：读 `diag-log.js` 发现它已被 task-7 按 H-10 改成**内存队列 + 定时批量 flush**（`queue/flushTimer/flushCount` 那套）。测试"写完立刻 `readFileSync`"必然读到还没刷盘的内容。单独用 `node -e` 复读同一文件时正则命中 → 证明断言内容本身没问题，是**时序**问题。
处置：测试里加 `waitFlush(ms)`（默认 600ms，气泡用例 2200ms），并在注释里写清原因 —— 后续任何人写"读日志"的断言都会撞上同一堵墙。
> 附带结论：这条坑本身说明 H-10 的修复是生效的（日志不再每条同步落盘），只是改变了依赖它的测试的时序假设。

### 坑 3：测试桩比真实实现"宽松"，导致一条断言假失败

`test-h01 §⑥`（没有 `dsh.previous` 时 `performRollback` 必须 `ok=false`）**失败**，实际 `{ok:true, to:'0.9.0-previous'}`。
定位：`scripts/lib/stage1-main-harness.js` 的 `rollbackDsh()` 桩无条件返回 `true`，而真实 `rollbackDsh()` 的第一行是"`dsh.previous/node_modules/@deepseek-ai/dsh/lib/bin.js` 不存在就 return false"。
处置：把桩改成**同一判据**（先查文件再返回）。这是本轮最重要的一条测试工程教训：**桩必须复刻被判据的语义**，否则测试会替实现"放水"。

### 坑 4：Unhandled rejection 噪声淹没有效信息

`test-h02 §⓪` 的对照实验（旧结构）会制造**无人接管的 Promise 拒绝**，Node 24 默认因此终止进程；而每个 `loadMain()` 都会注册一次 `process.on('unhandledRejection')`（main.js 自带），于是 5 次装载 → 5 条重复噪声。
处置：把对照实验提到最前面，并用一次性 `process.on('unhandledRejection', noop)` 兜住、跑完 `removeListener`。结果：1 条噪声（且它本身就是"旧结构会静默失败"的证据），不再污染后续用例。

### 坑 5（非缺陷，仅记录）：`ensureSeeded` 是不可超时的

设计超时时试图"给整条启动链一个总预算"，读到 `whenReady` 里 `mgr.ensureSeeded()` 是同步解压后发现：**同步阻塞期间计时器不会跑**，写一个"覆盖全流程"的 deadline 只会是自我安慰。
处置：只对三个**异步等待**阶段设 deadline（spawn/health/paint），并在 `main.js` 该步骤上写明"这里刻意没有超时，因为它不可超时"。这条是"禁止假装"纪律的直接应用。

## 4. 关键决策（为什么这么选）

| 决策 | 备选 | 选了 | 理由 |
|---|---|---|---|
| 超时是否"一刀切总预算" | 单个 180s 总预算 | 分三段（120/60/60） | 用户/支持者要能回答"卡在哪一步"；三种故障的处置方式不同（重试/换端口/看页面） |
| 超时后是否直接退出 | 退出 + 让用户重开 | reject → **既有** `showFatal` | 不新增失败出口，弹窗/托盘自救入口/崩溃报告全部沿用已验收的路径 |
| 失败计数放内存还是落盘 | 内存变量 | 落盘 `startup-recovery.json` | 两次失败之间必然重启一次进程，内存计数归零 = 永不触发 |
| 自动回滚上限 | 不限 / 每次失败都回滚 | **本轮 1 次** | 再回滚会消费掉磁盘上仅剩的旧版本，并进入"重启—回滚"死循环 |
| 自动回滚提示怎么弹 | 回滚前弹（阻塞） | 暂存台账 → 下次启动**非阻塞**弹一次 | 回滚后立刻 `app.relaunch()`，回滚前的弹窗活不过重启 |
| AUMID 字符串来源 | 常量/字面量 | `require('./package.json').build.appId` | 与安装器同源；两处分叉会被系统静默丢弃 |
| 气泡被吞怎么办 | 直接只用 Notification | 保留气泡为**主通道** + `balloon-show` 取证 + 仅在观测失败时补发 | 不允许"猜"；也不允许悄悄换通道 |
| 测试怎么驱动 `main.js` | 复制实现到测试 / 起真 Electron | `Module._compile` + 桩编译**真实 main.js** | 复制实现对真代码零覆盖（0.3.44 的教训）；真 Electron 无法在无桌面会话里跑 |

### 坑 6：出包门禁的识别正则漏掉它自己文档里的命名（**上报项**）

第一次跑 `node scripts/app-identity-gate.js`，【2】仍报"仓库根找不到任何 appId 形状的常量模块"——而
`app-identity.js` 里明明写着 `const APP_ID = 'com.deepseek.dshdesktop';`。

定位：读门禁源码第 53 行正则
`/(?:const|let|var)\s+([A-Za-z_$][\w$]*APP[\w$]*ID[\w$]*)\s*=\s*['"]([^'"]+)['"]/g`。
`[A-Za-z_$]` 已经吃掉首字母，**`APP` 不可能出现在名字开头**。写探针实测：

```
NO-MATCH   << const APP_ID = 'com.deepseek.dshdesktop';
MATCH   DSH_APP_ID   << const DSH_APP_ID = 'com.deepseek.dshdesktop';
NO-MATCH   << const APP_USER_MODEL_ID = 'com.deepseek.dshdesktop';
MATCH   DSH_APP_USER_MODEL_ID   << const DSH_APP_USER_MODEL_ID = 'com.deepseek.dshdesktop';
```

即：门禁注释里举的两个例子（`APP_ID`、`APP_USER_MODEL_ID`）**都过不了它自己的正则**。
处置：规范常量名定为 `DSH_APP_ID`（带前缀 —— 修正前/修正后两种正则下都命中，向前兼容），
别名保留 `APP_ID`/`appId`；把这条脆性写进审计 §7.1 上报（建议 `[A-Za-z_$][\w$]*APP` → `[\w$]*APP`）。
